## 0. 한 문장 결론

**구조전환은 이미 끝나 있다.** `han` 지도는 처음부터 縣=프로빈스 / 郡=스테이트로 구워져 있고,
그 소속 정보는 `infra/src/main/resources/map/han.json` 의 `cities[].meta.jun` 에 **780개 城 전부**
들어 있다. 빠진 것은 딱 하나 — 그 소속을 **Kotlin 런타임이 읽을 길이 없다**는 것이다.
`RawCity`/`CityInitialDetail` 에 郡 축이 없어서, 이미 郡을 요구하도록 설계된
`OfficerTitles.cityKindOf(jun, …)` 이 **프로덕션 호출자 0개**인 채로 죽어 있다.

따라서 이 작업은 "郡 노드 51개를 삭제·병합하고 인접을 다시 잇는 마이그레이션"이 **아니다.**
**삭제할 노드도, 재분배할 스탯도, 끊길 간선도 없다.** 필요한 것은 생성기가 이미 아는 郡 소속을
Kotlin 인덱스 하나로 더 뱉고, 그것을 변형(variant)·API·지도에 배선하는 것이다.

팀리드가 준 전제 중 **틀린 것 3개를 먼저 정정한다** — 실측 근거는 §1 에 있다.

| 전제 | 판정 | 실측 |
|---|---|---|
| "郡·國 51개가 縣과 같은 층에 노드로 섞여 있다" | **틀림** | 780 城 전부가 縣급 城이거나 郡治(治所)다. 별도 郡 노드는 **0개**. 51은 *이름이 군/국/윤으로 끝나는 城*을 센 것이고, 그중 47개는 治所(그 郡의 대표 城 — 있어야 할 노드), 4개는 오탐(安国县·襄国县·昌国县·冠军县 — 縣인데 한글 독음이 '…국/…군') |
| "인접 간선 郡-郡 28 · 郡-縣 122 가 사라진다" | **성립 안 함** | 그 간선들의 한쪽 끝은 治所다. 治所를 지우면 그 郡이 통째로 지도에서 사라진다. 아무것도 지우지 않으므로 간선도 그대로다 |

### 0.6 **출처 없는 수는 기준이 될 수 없다** — 팀 리드가 준 수치도 마찬가지다

> **팀 리드가 준 수치라도 출처가 명시되지 않으면 UNKNOWN 이다.**
> **합격 기준은 `han.json`·`han-tiles.json` 실측(780 · 175 · 1783 · 47)에서만 나온다.**
> **`junguozhi` 유래 수도, 대화에서 인용된 수도 기준이 될 수 없다.**
> **기준으로 쓰려면 그 수를 만든 명령을 문서에 적어라.**

이 규칙이 생긴 이유: `main_ratio >= 0.98` 외 3개가 **지어낸 수였는데** 문서가 그것을
「상위 지시가 준 목표치」로 격상해 **구현 요구사항으로 만들 뻔했다**(§4.0-c).
없는 것을 인용한 것이 1차 오류라면, **그 수로 남이 코드를 쓰게 만드는 것이 2차 오류다.**

### 0.7 **결함을 「드러내는 검사」와 「고치는 규칙」을 분리해라**

> **검사는 안전하고 규칙은 파괴적이다.**
> 결함을 발견하면 먼저 **그것을 드러내는 검사**를 붙여라. **파싱·정규화 규칙을 고치는 것은
> 그다음이고, 반드시 전수 diff 를 동반한다.**

이 규칙이 생긴 이유(2026-08-24 실증): 「縣名에 `，` 금지」를 **검사가 아니라 파싱 규칙으로**
구현했더니 `汝南郡`에서 진짜 縣 `北宜春`·`鮦陽` 이 사라지고 가짜 `章` 이 들어왔는데
**`cities 37=37` 체크섬은 통과했다.** R40(河南尹 상쇄)과 **정확히 같은 형태**다 —
개수 검사는 「빠짐 + 가짜」의 상쇄를 못 본다.

**따라서 텍스트 파싱 변경에는 105 郡國 전수 isolation diff 를 붙여라.**
「이 郡의 縣 목록이 변경 전후로 어떻게 달라졌는가」를 105줄로 출력하고 사람이 읽는다.
개수만 비교하는 검사는 **이 클래스의 결함에 대해 구조적으로 눈이 멀었다.**
싸 보이는 것과 안전한 것은 다르다.

### 0.4 **합격 기준의 출처 규칙** — 이것 하나가 남은 위반을 전부 거른다

> **`junguozhi` 에서 유래한 수는 합격 기준이 될 수 없다.**
> **`han.json`·`han-tiles.json` 에서 유래한 수만 기준이 된다: 780 · 175 · 1783 · 47.**

`junguozhi.json` 의 md5 가 **한 세션에 네 번 바뀌었다.** 縣 수·PASS 수·`CANDIDATE_REGION` 수·
`BLOCK` 수·A/B/C 갈래 분할·`seat` 값이 전부 그 위에 있다. **본문에 그 수가 남아 있으면
서술이지 기준이 아니다.** 검증 조건·assert·테스트에는 위 네 수만 써라.

**갈래 A/B/C 분할도 이 규칙에 걸린다** — 「`junguozhi` 가 治所 縣을 준다」가 A 의 정의이므로
**A/B/C 경계는 전적으로 파서 산출물에 의존한다.** 불변인 것은 **합 47** 하나뿐이다.

### 1.1 두 산출물, 하나의 진실

### A. 郡 이름을 단 治所를 어떻게 처리하나 — **개명한다. 병합·삭제는 없다**

사용자 결정: 治所 城은 治所 縣의 이름을 갖는다. 郡 이름은 `jun` 속성으로만 남는다.

#### A.1 개명 대상 — **「정확히 31」은 틀렸다. 47을 세 갈래로 가른다** (2026-08-24 재계수)

**1차 분류표가 46으로 합산됐고 47이 맞다.** 빠진 것은 **id 200 `감릉군`(甘陵郡, 郡=清河國,
기주, level 중)** 이다. 後漢 안제가 清河國을 甘陵으로 고친 사례라 명백한 개명 대상이다.

**그리고 「10 + 21 = 31」 자체가 틀렸다.** 근거를 `junguozhi.json` 에 실제로 물어보면 갈래가 다르다:

```
python3 - <<'EOF'
import json
cs=json.load(open('infra/src/main/resources/map/han.json'))['cities']
P={p['name']:p for p in json.load(open('data/map/junguozhi.json'))['places']}
seat=[c for c in cs if c['name'][-1] in '군국윤' and c['meta']['isSeat']]
a=[c for c in seat if P.get(c['meta']['junCh'],{}).get('seat')]
print(len(seat), len(a), len(seat)-len(a))
EOF
# → 47 12 35
```

**개명 대상 = A 11 + C 20 = 31. B 16은 손대면 사료를 망친다.**
**단 11·20·31 은 UNKNOWN 등급이다 — 아래 ⚠️ 를 읽어라.**

> **`遼東屬國`(id 729, `HanCityConst.kt:745`)은 갈래 B 다 — 재확인했고 유지한다.**
> `junguozhi` 가 `seat=雒陽` 을 주지만 **명백한 오류다.**
>
> **다만 앞 문장의 근거는 틀렸다: 「屬國은 縣을 두지 않는다」는 사실이 아니다.**
> 底本 `data/chgis-source/junguozhi/wu.html` 을 직접 읽으면 **縣이 실려 있다**:

> 확대 적용하는 것은 사료가 아니라 추론이다. → **개명할 이름이 UNKNOWN 이라서 개명하지
> 않는 것이 아니라, 개명이라는 조작 자체가 이 종류에 정의되지 않았다.**
>
> **표시 규칙**: 갈래 B 의 屬國 3건은 「개명 금지 · **개명 대상 이름 UNKNOWN**」으로 표기한다.

#### A.3 "(가) 治所 縣이 이미 별도 노드로 존재" — 병합이 아니라 **동명 충돌** 문제다

상위 지시가 "병합하나? 스탯은? 인접 합집합은? 자기루프는?" 를 물었다.
**전부 해당 없다 — 개명은 노드를 지우지 않기 때문이다.**

| 물어본 것 | 답 |
|---|---|
| 병합하나 | **아니다.** 노드 수는 780 그대로 |
| 스탯 합산/최대/유지 | **해당 없음.** 옮길 스탯이 없다. `RawCity` 스탯은 `level` 하나로 결정된다(`build_han_world.py:588`). 개명은 `level` 을 안 건드린다. **게임 균형 영향 0** |
| 인접 합집합 | **해당 없음.** 간선 1783개 그대로 |
| 자기루프 | **발생하지 않는다.** 자기루프는 인접한 두 노드를 **하나로 합칠 때** 생긴다. 합치지 않는다 |
| 대칭성 | **깨지지 않는다.** `link()`(`:524-527`)가 양방향으로 넣고, 개명은 그 뒤 이름 렌더링 단계다 |

**진짜 위험은 하나뿐: 개명 결과가 기존 城 이름과 겹치는 것.**
상위 지시가 지목한 `낙릉군`(383)→`낙릉` 이 `낙릉`(362)과 겹치는 경우다.
그리고 **그 둘은 서로 인접해 있다**(§1.3).

**이것이 치명적인가 — 아니다. 실측:**

| 사실 | 값 |
|---|---|
| 지금 이미 존재하는 동명 이름 | **57개 (城 127개)** — 기×4, 노×4, 유×4, 영릉×3 … |
| 지금 이미 **인접한 동명 쌍**을 가리키는 path 항목 | **4개** |
| `HanCityConstVariant` 재해석의 간선 정확도 | **1783/1783, 소실 0 · 날조 0**(§1.4) |
| path 항목 총수 | 3566 |
| 이름 후보가 2개 이상인 path 항목 | 568 |
| **상호참조 필터 후에도 후보가 2개 이상 = 순서에 의존해 찍는 항목** | **12** |

즉 동명은 **이미 이 지도의 정상 상태**이고, 런타임 해석기가 그것을 견디고 있다.
개명이 새 동명을 몇 개 만들어도 12라는 취약 항목이 조금 늘 뿐 구조가 깨지지 않는다.

**단, `CityConst.generateCities()` 의 `nameMap[raw.name] = raw.id` last-wins 는 여전히 살아 있다** —
`base.constName` 이 그걸로 만들어지고 `byName()` 이 그걸 쓴다. 상위 지시가 지목한 그 함정이 맞다.
지금도 57개가 그렇게 덮여 있고, `CityConstRegistry.kt:247-252` 주석이 이미 경고한다.
**대응: 새 코드는 城을 id 로만 가리킨다.** `byName()` 을 새로 부르지 마라(§7 R9).

#### A.5 자동 검사 (상위 지시가 "반드시 있어야 한다"고 한 것)

`build_han_world.py` 의 `collisions` 계산(`:483-485`)이 **이미 동명을 세고 요약에 찍는다.**
사다리 2단 — 새로 만들지 말고 그 옆에 **개명이 새로 만든 충돌만** 골라내는 세 줄을 붙인다.

```python
# names 확정 직후, collisions 계산 옆.
before = Counter(base_name(ci) for ci, _ in order)          # 개명 전 이름 분포
new_dup = sorted(n for n, k in dup.items()
                 if k > before.get(n, 0) and n in SEAT_NAMES.values_as_names)
stats["renameCollisions"] = new_dup
```
그리고 `summary()` 에 한 줄:
```
print(f"개명이 새로 만든 동명 {len(stats['renameCollisions'])}: "
      + (", ".join(stats["renameCollisions"]) or "없음"), file=e)
```

**게이트로 쓸 것 — 다음 셋을 `build()` 끝에서 `assert` 한다** (실패하면 생성 자체가 죽는다):
1. `len(names) == len(order) == 780` — 개명이 城을 잃지 않았다
2. `sum(len(v) for v in conn.values()) // 2 == 1783` — 간선 수 무변
3. `SEAT_NAMES` 의 모든 키가 실제 `juns[].nameCh` 에 존재 — 오타난 郡 이름이 조용히 무시되지 않는다

3번이 없으면 `SEAT_NAMES["遼東郡"]` 을 `"辽东郡"` 로 잘못 써도 아무 일도 안 일어난다.
**동결된 타일 파일이 간체(`雒阳县`)와 번체를 섞어 쓰므로 이 실수가 실제로 일어난다.**

**동명이 0이어야 하는가 — 아니다.** 이미 57개다. 0 을 목표로 하면 사료 이름을
비틀어야 하고, 그건 `build_han_world.py:479-481` 이 명시적으로 거부한 방침이다
("접두나 번호를 붙여 이름을 비트는 대신 겹치는 채로 두고, 몇 건인지만 보고한다").
**목표는 0 이 아니라 "몇 건인지 알고 있는 것"이다.**

### C. `RawCity` 스키마를 어떻게 바꾸나 — **바꾸지 마라. 별도 인덱스를 낸다**

**채택안: `HanJunIndex.kt` 를 생성기 산출물로 하나 더 뱉고, `CityConstVariant` 에
`gateKeys()` 와 똑같은 모양의 접근자를 얹는다.**

근거 — 저장소에 이미 **똑같은 문제를 똑같이 푼 선례**가 있다. `HanGateIndex.kt` 는
郡 단위로 계산한 게이트 키를 城 id 로 뿌린 `Map<Int, Set<String>>` 이고, 같은 생성기가 뱉고,
`CityConstVariant.gateKeys(cityId)` 가 기본 빈 집합으로 열려 있다(`CityConstRegistry.kt:106`).
郡 소속도 정확히 같은 형태의 데이터다. 사다리 2단(이미 있는 패턴 재사용)에서 멈춘다.

```kotlin
// common/.../HanJunIndex.kt — GENERATED
object HanJunIndex {
    /** 城 id → 소속 郡 이름(한글). 780/780. */
    val junByCityId: Map<Int, String>
    /** 郡 이름 → 治所 城 id. 175/175. */
    val seatByJun: Map<String, Int>
    /** 郡 이름 → 그 郡에 속한 城 id 전부(治所 포함, id 오름차순). */
    val citiesByJun: Map<String, List<Int>>
}
```
`CityConstVariant` 에 기본 구현이 빈 값인 3개 접근자를 추가한다:
```kotlin
fun junOf(cityId: Int): String? = null
fun seatOfJun(jun: String): Int? = null
fun citiesOfJun(jun: String): List<Int> = emptyList()
```
`HanCityConstVariant` 만 `HanJunIndex` 로 override 한다. che·miniche 는 무변.

**기각한 대안과 이유:**

- **`RawCity`/`CityInitialDetail` 에 `jun: String = ""` 추가.** `RawCity` 는 뒤에 붙이면
  `cheInitCity` 94행·`minicheInitCity` 78행의 위치 인자가 살아남긴 한다. 문제는
  `CityInitialDetail` 이다 — 이건 `generateCities()`(팀리드가 지목한 byte-identical 포팅,
  "last-wins quirk" 까지 보존한 코드)의 **출력물이자 data class** 다. 필드를 늘리면
  `equals`/`hashCode`/`toString`/`copy` 가 전부 바뀌고, che 패리티 골든이 `CityInitialDetail` 을
  직·간접으로 직렬화·비교하는 지점이 있으면 그대로 깨진다.
  **이 리스크를 감수할 이유가 없다** — 얻는 값이 인덱스 하나로 똑같이 얻어지기 때문이다.
  (참고: 실제로 골든이 깨지는지는 **검증하지 않았다.** 검증하지 않아도 되도록 이 안을 버렸다.)
- **`RawCity` 만 늘리고 `CityInitialDetail` 은 그대로.** `generateCities` 안에서 `jun` 이
  버려지므로 런타임에 도달하지 않는다. 결손 G1 을 못 푼다.
- **DB `city` 테이블에 `jun` 컬럼 추가.** 城 id 로 완전히 결정되는 정적 상수다. 마이그레이션·
  중복 진실 소스만 늘고 얻는 게 없다. 하지 마라.

**`constRegion` 같은 `constJun` 맵이 필요한가 — 아니다.** `constRegion` 의 존재 이유는
PHP `byRegion()` 의 last-wins quirk 패리티 재현이다. 郡에는 대응하는 PHP 함수가 없으므로

### 0-c단계 — **연결성 검사: 없다. 그리고 그 네 숫자는 근거가 없다** (2차 정정)

**1차 정정은 절반만 갔다.** 「구현이 없다」까지는 맞았는데 **네 숫자를 「상위 지시가 준 목표치」로

유령을 지웠더니 유령이 스펙이 됐다.**

**정정: `main_ratio >= 0.98` · `isolated < 15` · `components < 20` · 郡 `edges >= 150` 은
출처가 없다. 실측·문서·코드 어디에서도 나오지 않는다. 전부 UNKNOWN 이다.**
(`grep -rn 'main_ratio'` 는 이 문서만 친다.)

**그리고 그 숫자는 실제보다 20배 느슨했다.** 현재 실측:

```
python3 - <<'EOF'
import json
from collections import deque, defaultdict
cs=json.load(open('infra/src/main/resources/map/han.json'))['cities']
adj=defaultdict(set)
for c in cs:
    for n in c['connections']: adj[c['id']].add(n); adj[n].add(c['id'])
ids={c['id'] for c in cs}; seen=set(); comps=[]
for i in ids:
    if i in seen: continue
    q=deque([i]); seen.add(i); cur=0
    while q:
        u=q.popleft(); cur+=1
        for v in adj[u]:
            if v not in seen: seen.add(v); q.append(v)
    comps.append(cur)
comps.sort(reverse=True)
print(len(ids), sum(len(a) for a in adj.values())//2, len(comps),
      comps[0]/len(ids), sum(1 for i in ids if not adj[i]))
EOF
# → 780 1783 1 1.0 0
```

| 지표 | **실측 기준선** | 지어낸 임계값 | 차이 |
|---|---:|---:|---|
| `components` | **1** | `< 20` | **19개까지 깨져도 통과** |
| `isolated` | **0** | `< 15` | 14개까지 통과 |
| `main_ratio` | **1.0** | `>= 0.98` | 15개 고립까지 통과 |
| 간선 | **1783** | — | — |

#### 따라서 절대 임계값이 아니라 **기준선 회귀 검사**를 만든다

> **`tools/scenario/tests/test_han_connectivity.py`(`unittest.TestCase`)**
> **커밋된 `han.json` 을 읽어 `components == 1` · `isolated == 0` · `main_ratio == 1.0` ·
> `edges == 1783` 을 assert 한다.** 기준선보다 나빠지면 즉시 실패한다.
> 기준선을 올릴 때(§13 확장·§20 세분)는 **테스트 상수를 함께 고치고 그 커밋에서 사람이 승인**한다.

- **CI 가 자동으로 줍는다** — `ci.yml:23` 이 `tools/scenario/tests` 를 `unittest discover` 한다.
  (`tools/map/tests` 도 `:22` 에서 discover 된다 — **둘 다 CI 대상이다.**
  `han.json` 이 scenario 도메인이라 scenario 쪽에 두는 것뿐이다.)
- **pytest 스타일 함수로 쓰지 마라 — `unittest discover` 가 수집하지 않는다.**

## 6. 되돌리는 법

> **§13.5 의 10.5~12.5단계(재추출·확장·좌표 메우기)는 git 으로 되돌릴 수 없다.**
> `data/map/junguozhi.json` 과 `data/chgis-source/**` 는 **gitignore** 라 워킹 트리에만 있고,
> 재추출은 그 파일을 **덮어쓴다.** 되돌릴 원본이 사라진다.
>
> **따라서 10.5단계 시작 전에 백업이 선행이다:**
> ```
> cp data/map/junguozhi.json data/map/junguozhi.json.bak-$(date +%Y%m%d%H%M)
> ```
> `.bak-*` 도 gitignore 대상이어야 한다(ADR-LITE-039 — 원본 파생물은 미커밋).
> **백업 없이 재추출한 사람은 이전 상태를 복원할 방법이 없다.**

단계별로 완전히 독립이고, 각각 되돌려도 나머지가 산다.

| 단계 | 되돌리기 |
|---|---|
| 2 | `git rm common/.../HanJunIndex.kt` + `build_han_world.py` 의 `OUT_JUN` 3곳 되돌림 → `--check` 통과 확인 |
| 3 | `CityConstRegistry.kt` 의 추가 3메서드 제거. 기본 구현이 빈 값이라 호출자 없으면 무해 |
| 4 | 테스트 파일 삭제 |
| 5 | `CityConstItem.jun` 은 nullable 기본값이라 제거해도 클라이언트가 안 깨진다 |
| 7 | 프런트 변경만 되돌림. 서버·상수는 무관 |

**전체 되돌리기**: 2·3·5 를 되돌리고 `python3 tools/scenario/build_han_world.py --check` 가
"드리프트 없음" 이면 **로컬 입력이 1단계와 동일하다는 전제 하에** 원복된 것이다.
`junguozhi.json` 이 그 사이 바뀌었으면 드리프트가 떠도 원복 실패가 아니다.
**단정적 판정은 `HanCityConst.kt` md5 가 1단계 기록과 같은지 하나뿐이다** — 그게 진짜 기준이다.

`main` 근처에 가지 마라. 실험은 전용 워크트리에서 해라.

### 8.5.2 그런데 175는 안 떨어진다 — 네 번째 실측

"별도 郡 노드 51개"는 §0·§1.3 에서 이미 세 번 기각된 전제다. 이번에는 국가 등급 축에서

      '그중 isSeat', sum(1 for c in suf if 4<=c['level']<=9 and c['meta']['isSeat']))
print([(c['name'],c['level']) for c in suf if not 4<=c['level']<=9])"
```

| 결과 | 값 |
|---|---|
| 이름이 군/국/윤 으로 끝나는 城 | 51 (level 소 44 · 중 3 · 영현 2 · 장현 2) |
| 그중 `countsForNationLevel` 참 | **47** |
| **그 47개 중 `isSeat=True`** | **47 — 전부다. 하나도 예외 없다** |
| 세지 않는 4개 | 안국(11)·양국(11)·창국(10)·관군(10) — **전부 `isSeat=False`** = §1.3 의 오탐 4개와 정확히 같은 집합 |

> **즉 128 은 "郡 노드를 지운 뒤의 수"가 아니라 "175개 治所 중 47개를 지운 뒤의 수"다.**
> 47개 治所를 지우면 **175개 郡 중 47개가 지도에서 통째로 사라진다.** §0.1 경고 상자의
> 그 작업이고, **실행하면 안 되는 것으로 이미 확정돼 있다.**
>
> 사용자가 결정한 것은 **개명**이다(§3.A, 31건). 개명은 `name` 만 바꾸고 `level` 은 안 건드린다.
> `countsForNationLevel` 은 `level` 만 읽는다(`UpdateNationLevel.kt:74`, `byId(cityId)?.level`).
> **집계 경로가 `byId` 라 이름 충돌과도 무관하다.**

### 8.5.3 결론 — 세 축 전부 **0줄**

| 항목 | 판정 |

### 8.5.4 3축 관등은 **별도로 더 위험하다**

단일 사다리만 보면 안 된다는 지적은 옳다. 3축은 **전역 175가 아니라 州별 郡治 수**를 본다
(`NationRank.kt:120-127`): 州牧 = 비율 ≥0.8 **AND 郡治 ≥5**, 刺史 = ≥0.5 **AND ≥3**, 나머지 太守.

`HanProvinceSeatsTest.kt:20` 이 실측 분포를 주석으로 박아 뒀다:
`{1=9, 2=8, 3=13, 4=8, 5=7, 6=7, 7=17, 8=13, 9=19, 10=17, 11=12, 12=15, 13=8, 14=22}`.

47개 治所를 지우면 **비율의 분모와 절대 하한이 동시에 움직인다.** 7개짜리 州(5·6)에서
치소가 몇 개만 빠져도 `郡治 ≥5` 인 州牧이 **구조적으로 도달 불가능**해진다. 문턱 배율
조정으로는 **이 축을 보정할 수 없다** — 州별 절대 하한은 배율의 대상이 아니다.
**보정 불가라는 사실 자체가 삭제안을 기각할 두 번째 독립 근거다.**

**개수 자체는 견딘다.** 실제로 못 쓰게 만드는 것은 **동명 57개(城 127개)** 다 —
드롭다운에 "영릉"이 세 줄 뜨고 어느 것이 어느 것인지 구분할 방법이 **지금 없다.**

**추천 (1줄 고침 우선):** `:88` 의 `info` 칸에 郡 이름을 넣는다.
그 칸은 현재 `LEVEL_TEXT[c.level] ?? String(c.level)` 인데, `LEVEL_TEXT`(`:14-16`)에

```
info: `${jun} · ${LEVEL_TEXT[c.level] ?? c.level}`     // 예: "영릉 · 零陵郡 · 장현"
```
`jun` 은 5단계에서 `/api/game/const` 로 온다. **2단 필터보다 이게 먼저다.**

**2단 선택(郡 → 그 안의 縣)은 그 다음이다.** 郡당 縣 수가 §1.2 기준 최대 23,
중앙값 한 자리다. 1차 필터로 유용하긴 하지만, 위 한 줄이 통하면 **필요 없을 수도 있다.**
한 줄을 먼저 넣고 실제로 쓰기 힘든지 보고 나서 결정해라.

> 상위 지시가 "郡으로 1차 필터(51개 → 그 안의 縣) 2단"이라고 했는데 **51이 아니라 175개**다(§1.2).
> 175개짜리 1차 필터는 그 자체로 또 하나의 긴 목록이다. 2단 선택을 만들 거라면
> **州(14) → 郡(175) → 縣** 의 3단이 되어야 실제로 짧아진다. 이것이 2단 선택을
> 나중으로 미루라고 추천하는 또 하나의 이유다.

## 12. 치소 = 郡의 급소 (스키마에 지금 넣는다)

사용자·팀리드 합의: **치소를 뺏기면 그 郡 소속 縣 전체가 보급·치안 페널티.**
"郡을 친다"가 縣 하나를 치는 것으로 환원되고 효과는 郡급으로 난다 — **별도 郡 전투 시스템 불필요.**

### 12.1 스키마 — §3.C 의 `HanJunIndex` 가 이미 이걸 담는다

새 필드가 필요 없다. `seatByJun: Map<String, Int>` 하나로 판정이 전부 나온다:

```kotlin
// CityConstVariant — §3.C 에서 이미 추가하기로 한 3개 접근자 그대로.
fun junOf(cityId: Int): String?        // 이 城이 어느 郡인가
fun seatOfJun(jun: String): Int?       // 그 郡의 급소는 어느 城인가
fun citiesOfJun(jun: String): List<Int> // 페널티를 받을 대상 전부
```
런타임 판정은 한 줄이다:
```kotlin
fun seatLost(cityId: Int, ownerOf: (Int) -> Int?): Boolean {
    val seat = junOf(cityId)?.let(::seatOfJun) ?: return false
    return seat != cityId && ownerOf(seat) != ownerOf(cityId)
}
```
**별도 컬럼·테이블을 만들지 마라.** 치소 소유는 `city` 행에서 그때그때 읽는다.
郡 상태를 저장하면 縣 소유와 어긋날 수 있는 두 번째 진실 소스가 생긴다(§8).

> **`isSeat` 를 `RawCity` 에 넣고 싶어질 것이다. 넣지 마라.**
> `seatOfJun(junOf(id)) == id` 로 나온다. 필드 하나를 아끼는 게 아니라
> **`CityInitialDetail` 을 안 건드리는 것**이 요점이다(§3.C 기각 사유).

### 12.2 페널티를 거는 지점 (구현 시)

`UpdateCitySupply` 와 치안 계산이 소비자다(§E). **이 명세는 페널티 수치를 정하지 않는다** —
게임 밸런스라 사용자 판단이다(U11). 스키마만 준비된다.

### 12.3 2번(이반 전파)을 나중에 받을 수 있는 모양인가 — **받는다**

이반 전파는 "같은 郡/州 이웃이 이미 넘어갔나"를 확률에 넣는 것이다. 그 질문에 답하려면
`citiesOfJun(jun)` 과 `region` 두 개가 필요하고, **둘 다 이 스키마가 이미 준다.**
이반 로직은 판정 함수 안에서 그 두 축을 읽기만 하면 되므로 **스키마 마이그레이션이 다시 필요하지 않다.**
3번(郡 전체 장악 보너스)도 `citiesOfJun` 전부의 소유를 세는 것이라 같다.

### 13.1 좌표 — 타일 재생성 없이 된다

`junguozhi.json` 의 `RESOLVED_POINT` 縣은 `lat`/`lon` 을 갖고 있고,
`tools/map/build_terrain_grid.py:50-63` 의 `Proj` 가 그것을 `col`/`row` 로 바꾼다(§1.6).
**`han-tiles.json` 을 읽기만 하고 쓰지 않는다 — #536 준수.**

> ⛔ **`RESOLVED_POINT` 는 「좌표가 맞다」는 뜻이 아니다 — R44.**
> `RESOLVED_POINT` 883건 중 **101縣이 남의 좌표를 공유한다**(고유 좌표 827, 45개 그룹).
> `五原郡`·`雲中郡` 의 縣들이 **353km·249km** 끌려가 있고 `廣漢屬國 陰平` 은 **1170km** 틀렸다.
> 근본원인은 **해석기가 郡을 무시하고 縣名만으로 CHGIS 사전을 조회**하는 것 — 동명 縣이
> 다른 郡의 좌표를 집어온다. 파서 담당이 수정 중이다.
>
> **따라서 확장 縣을 지도에 찍기 전에 「좌표가 유일한가」를 먼저 검사해라.**
> 중복 좌표는 **드러내는 검사**로 잡고(§0.7), 자동 보정하지 마라.
> 재현: `collections.Counter((c['lat'],c['lon']) for j in places for c in j['counties'] if c['resolution']=='RESOLVED_POINT')` 에서 `v>1` 인 그룹.

### 13.2 스탯 — 신규 縣은 **기존 縣과 똑같이 나온다** (상위 지시의 "진짜 난점"에 대한 답)

**난점이 아니다.** `RawCity` 의 6개 스탯은 이미 **개별 사료값이 아니라 `level` 하나에서 파생**된다:
`build_han_world.py:588` 의 `maxes[lv]` — `lv` 는 治所면 郡 등급, 縣이면
`county_level(jn)`(郡戶÷縣수를 「萬戶以上為令」 경계에 댄 값)이다.
**같은 郡의 縣은 통째로 같은 스탯을 받는다.** 실측이 그것을 보여준다 — 縣 780행 중
`장현` 380개가 전부 `587, 11, 11, 8, 12, 11` 로 동일하다.

따라서 신규 縣도 소속 郡만 알면 **기존 縣과 완전히 같은 경로로 스탯이 나온다.**
새 배분 규칙을 발명할 필요가 없다. `households` 를 縣으로 나누는 작업도 이미 되어 있다.

**`generateCities` 바이트동일 포팅과의 충돌 — 없다.** 신규 縣은 `HanCityConst.kt` 의
`RawCity` 행이 늘어나는 것이고, `generateCities` 는 행 수에 무관한 순수 변환이다.
che·miniche 의 입력은 한 행도 안 바뀐다. **패리티 골든 무영향.**

> 단, `county_level` 의 분모가 `len(p["counties"])` = **郡國志의 縣 수(1076 기준)** 이지
> 게임에 올라온 縣 수가 아니다(`build_han_world.py:445-455`). 縣이 늘어도 **등급은 안 변한다.**
> 이건 의도된 것이다 — 사료의 縣 수가 분모여야 「郡戶÷縣수」가 사료값이 된다.

### 13.3 인접 간선 — 신규 縣은 **차수 1의 잎**이 된다

`adjacency.county`(타일의 2661 간선)는 타일 城 인덱스로 매겨져 있고,
**신규 縣에는 그 간선이 없다.** 생성기의 연결 규칙 중 신규 縣에 걸리는 것은
규칙 2(`縣 ↔ 자기 郡 治所 직결`, `build_han_world.py:466`) 하나뿐이다.

따라서 104개 신규 縣은 **각자 治所에 붙은 잎 하나**가 된다.

| | 지금 | 13-A/B 후 (예측) |
|---|---|---|
| 城 | 780 | 884 |
| 간선 | 1783 | 1887 (+104, 전부 治所 직결) |
| 연결 성분 | 1 | **1** |
| 고립 | 0 | **0** |

**연결 성분 1 · 고립 0 이 유지된다 — 기준선 회귀 검사(§4.0-c)를 통과한다는 뜻이다.**
잎은 고립이 아니다. 위 숫자는 규칙에서 나온 **예측이고, 13-A 구현 후 실측으로 대체해야 한다.**
(앞 판정이 인용한 `main_ratio >= 0.98` 등 네 임계값은 **근거 없는 수였다 — §0.6.**)

**얻는 것과 잃는 것을 정직하게:**
- 얻음: 郡國志 縣 104개가 지도에 이름과 위치를 갖고 나타난다. 내정 슬롯이 늘고 郡이 두꺼워진다.
- 잃음: 그 縣들은 **막다른 길**이다. 이웃이 治所 하나뿐이라 통과 경로가 되지 못한다.
  `CalcCityDistance` 거리가 실제 지리보다 멀게 나온다(治所를 반드시 경유).

**추천: 그대로 간다.** 잎이라도 있는 것이 나은 이유 —
(1) 이동·출병이 1칸 제한이라(`SelectCityField.tsx:32-37`) 잎도 정상 목표다,
(2) 나중에 인접을 보강할 때 **노드가 이미 있어야** 간선만 얹으면 된다,
(3) 지어낸 간선을 넣는 것보다 없는 게 낫다.

> **간선을 근접 거리로 자동 생성하지 마라.** 그게 #536 이 터진 방식(타일 재생성 시
> 인접 2662→1230)이고 #541 이 터진 방식(좌표 근접 추정)이다. 잎으로 두는 것이 안전하다.

### 13.4 `CANDIDATE_REGION` 288개 — **좌표 문제가 아니라 파서 잔여물이다** (2026-08-24 정정)

앞선 판정("좌표가 없으니 넣지 마라")은 **결론은 맞았지만 이유가 틀렸다.** 288의 정체를
생성기에서 확인했다 — `tools/map/build_junguozhi.py:295-303`:

```python
extra = []
if gap > 0:                                  # gap = 선언 城數 - 매칭된 縣 수
    known = {c['name'] for c in got}
    for _, w in sorted(b['residual']):       # ← residual = 매칭 실패한 잔여 단어
        if w in known or len(extra) >= gap: continue
        known.add(w)
        extra.append(dict(name=w, note='', tags=[], lon=None, lat=None,
                          resolution='CANDIDATE_REGION'))
```

**`CANDIDATE_REGION` 288 = `extra` 288 이다**(실측: `sum(resolved)=788`, `sum(candidate)=288`).
즉 이건 "좌표를 못 찾은 縣" 목록이 아니라 **파서가 매칭에 실패한 잔여 단어를 城數 차이만큼
채워 넣은 버킷**이다. 실제 내용:

```
梁 熒陽 菀陵 睪 匽師 睾 楊 陽陵 槐里 水 八年復 垂山 汧 渝麋 雍 襄 衝陵 國
道亭 鮦陽 元中復 宋 公國 定潁 山 國 穀陽譙 鄲 國 鉅鹿 斥 在西北 南深國 武 …
```

`國`·`水`·`山`·`丘`·`斥`·`八年復`·`在西北`·`城中` 은 縣 이름이 아니라 **郡國志 주석 문장의
파편**이다. 반대로 `熒陽`·`菀陵`·`槐里`·`汧`·`雍`·`鮦陽`·`濮陽`·`范`·`鉅鹿` 은 실존 縣이다.
`穀陽譙`(穀陽+譙)·`羡邾`(沙羡+邾) 는 두 縣이 붙었고, 樂浪郡의 `浿`+`水`(浿水)·`帶`+`方`(帶方) 은
반대로 쪼개졌다. `睪` 은 成皐(成睾)의 잔여물로 보인다.

> **따라서 288에 좌표를 붙이는 작업은 시작부터 잘못된 작업이다.**
> 이름 목록 자체가 틀렸는데 좌표를 붙이면, 문장 조각에 위경도가 달린 城이 지도에 뜬다.
> **#541 보다 나쁘다** — #541 은 진짜 지명에 틀린 좌표였고, 이건 지명도 아닌 것에 좌표다.
> `namu-places` 가 확보한 288 중 **114건의 현대 비정 좌표도 재추출 전에는 쓰지 마라** —
> 붙일 이름이 확정되지 않았다.

### 13.4-b `resolution` 에 나무위키 좌표를 섞을 것인가 — **`source` 필드를 분리한다**

`namu-places` 가 미확정분 중 114건의 현대 비정 좌표를 확보했다. 그 좌표는 **어느 사서에도
없고 나무위키 편집자의 비정이다.** 지금 스키마는 `resolution ∈ {RESOLVED_POINT,
CANDIDATE_REGION}` 두 값뿐이라 CHGIS 유래와 위키 유래가 구분되지 않는다.

| 안 | 판정 |
|---|---|
| `resolution` 에 제3 등급(`RESOLVED_SECONDARY`)을 추가 | **거부.** `resolution` 은 **"좌표가 점으로 확정됐는가"** 라는 한 가지 질문에 답하는 필드다. 여기에 출처를 섞으면 **소비자가 전부 3분기로 바뀐다** — 지금은 `== 'RESOLVED_POINT'` 한 줄이면 되는 판정이 등급 목록 비교가 된다. 축이 둘인데 필드가 하나면 나중에 네 번째 출처가 생길 때 또 등급이 는다 |
| **`source` 필드를 따로 둔다** | **채택.** `resolution` 은 그대로 두 값, `source ∈ {CHGIS, NAMU, MANUAL}` 를 **직교하게** 추가. 게임 코드는 `resolution` 만 보면 되고(변경 0), 감사·승격·롤백은 `source` 로 한다 |

```jsonc
{ "name": "濮陽", "lat": 35.70515, "lon": 115.01371,
  "resolution": "RESOLVED_POINT",     // 좌표가 점으로 있는가 — 게임이 보는 축
  "source": "NAMU",                   // 그 좌표가 어디서 왔는가 — 사람이 보는 축
  "sourceNote": "나무위키 東郡 濮陽縣 항목" }
```

**근거 3가지**: (1) 게임에는 어차피 좌표가 필요하니 등급을 나눠 봐야 렌더링은 같다 —
축을 나누면 **소비자 코드가 한 줄도 안 바뀐다.** (2) #541 의 교훈은 "출처를 데이터에
남겨라"이지 "출처별로 동작을 바꿔라"가 아니다. 출처가 남아 있으면 **한 줄 필터로 일괄
롤백**할 수 있다(`source != 'NAMU'`) — 등급으로 섞으면 못 한다. (3) `source` 없는 기존
항목의 기본값을 `CHGIS` 로 두면 **마이그레이션이 없다.**

**전제 조건**: 나무위키 좌표 반영은 **재추출(13.4-a) 이후에만.** 이름이 확정되기 전에
좌표를 붙이면 문장 조각에 좌표가 달린다.

### 13.4-c `seat` 을 治所 근거로 쓸 때의 방어 — **믿되 검증한다** (상위 지시 정정 반영)

**상위 지시가 정정됐다.** 「治所는 `counties[0]`/`seat` 에서 가져와라」는 유효하되
**`counties[0]` 자체가 파서 산출물이라 쓰레기일 수 있다.**

#### 먼저 범위를 좁힌다 — 이 오염은 **제1부를 건드리지 않는다**

| 무엇 | 治所가 어디서 오는가 | `junguozhi.seat` 오염 영향 |
|---|---|---|
| **게임 지도의 治所 175개** | `han-tiles.json` 의 `juns[jn]["seat"]` (타일 인덱스) — `build_han_world.py:427-441` | **없음.** `junguozhi` 를 안 읽는다 |
| 縣 확장(§13) · 좌표 메우기(§20.6) · 郡 유니크(§19) | `junguozhi.json` 의 `counties` / `seat` | **직격** |

**따라서 제1부(개명·`HanJunIndex`·토글·커맨드 UI)는 파서 결과를 기다릴 이유가 없다.**
**대기해야 하는 것은 §13 확장과 제2부의 좌표 의존 항목뿐이다.**

#### 방어 규칙 (구현자가 그대로 코딩할 것)

`seat` 을 소비하는 코드는 **먼저 신뢰 등급을 매기고, BLOCK 은 진행을 막는다.**

```python
# BLOCK 조건 — 둘 중 하나라도 걸리면 그 郡의 seat 은 쓰지 않는다
def seat_blocked(place, lexicon) -> bool:
    return place.get('checksum') != 'PASS' or place['seat'] not in lexicon
```

실측 (06:38 기준):

| 등급 | 郡 수 | 뜻 |
|---|---:|---|
| **BLOCK** | **32** | `checksum != PASS` **또는** `seat ∉ CHGIS 어휘` |
| 조건부 신뢰 | 70 | 위 둘 다 통과. **"검증됨"이 아니라 "자동 탐지에 안 걸림"이다** |
| `seat` 자체가 없음 | 3 | 屬國 3개(`廣漢屬國`·`張掖屬國`·`遼東屬國`) — `counties` 가 빈 배열 |

BLOCK 판정에 걸린 실제 쓰레기 예(측정 시점마다 수가 달라진다): `益州郡 seat=北`(원문 滇池), `遼東郡 seat=無`,
`安定郡 seat=臨`, `交趾郡 seat=龍`(龍編 절단), `玄菟郡 seat=高句`(高句驪 절단),
`酒泉郡 seat=戶萬`, `九江郡 seat=浚遒` (縣 5개만 추출 — 壽春 없음).

**어휘 검사는 판정이 아니라 선별이다.** 걸린 21건 중 `濮陽`·`槐里`·`臨菑`·`姑臧`·`晉陽`·

그래서 BLOCK 은 "틀렸다"가 아니라 **"사람이 봐야 한다"** 는 뜻이다.

### 16.1 슬롯 수 = `level` 의 함수 (**제안값 — 미확정**)

> **⚠ 이 분포는 §4 0단계가 바꾼다** — `소110 중31 대14 특11` 로 이동한다.
> **0단계 이후 재계산하고 슬롯 합계를 다시 내라 — U29.** 지금 값을 확정으로 쓰지 마라.

```kotlin
// 제안 — 수치 미확정
// CityConstVariant 의 확장 지점으로 낸다. 기본 구현이 0 이므로 che 는 손댈 필요가 없다.
open fun slotCount(level: Int): Int = 0          // CityConstVariant 기본값

// HanCityConstVariant 만 오버라이드한다
override fun slotCount(level: Int): Int = when (level) {
    9 -> 6; 8 -> 5; 7 -> 4; 6 -> 3; 5 -> 2; 4 -> 2   // 주정착지(治所)
    10, 11 -> 1                                       // 소정착지 — 고정 1
    else -> 0                                         // 관문·전장(3) 등
}
```

> **정정 — 앞 초안의 「`else -> 0` 이 che 를 자동 배제한다」는 틀렸다.**
> **che 의 level 은 1..8 이고 `소`=5·`중`=6·`대`=7·`특`=8 로 han 과 숫자가 겹친다**
> (`CityConst.kt:30-33`). 단일 `when` 은 숫자만 보므로 **che 69개 城이 슬롯 2~5를 받는다.**
> **반드시 변형별 분기여야 한다** — `gateKeys`/`countsForNationLevel` 과 같은 형태로
> `CityConstVariant` 에 기본 0 을 두고 han 만 오버라이드한다.
> **빨간 프로브: che 변형으로 `slotCount(8)` 을 불러 0 이 아니면 실패하는 테스트를 먼저 심어라.**

> **슬롯은 `level` 을 읽기만 한다. 슬롯을 이유로 `level` 을 조정하지 마라.**
> `level` 은 표시값이 아니라 **국력 계산 입력**이다(`UpdateNationLevel.kt:78·518`,
> `countsForNationLevel(level in 4..9)`). 등급을 하나 올리면 그 城이 국가 등급 집계에
> 들어가고 3축 州別 郡治 수까지 움직인다. **§8.5 참조.**

**분포를 보고 정한 근거** (지시대로 실제로 세고 판단했다):

- **상위 등급이 극단적으로 희소하다.** 대+특+경 = **27城(3.5%)**. 곡선을 가파르게 잡으면
  27개가 게임을 지배한다. 최고(6)와 최저(1)의 폭을 **6배로 좁게** 잡았다.
- **治所의 과반(111/175)이 '소'다.** 치소라고 다 큰 도시가 아니다. **소=2 가 표준 治所**이고
  여기가 밸런싱 기준점이다. 앞 초안의 소=3은 治所 전체 슬롯의 3분의 1을 한 등급에 몰았다.
- **주정착지 최저(2) > 소정착지(1).** 治所가 자기 縣보다 슬롯이 적은 경우가 없어야 §12
  급소 서사가 성립한다. **역전 금지를 불변식으로 테스트에 박아라.**
- **총 1053슬롯 중 605(57%)가 소정착지의 고정 1칸이다.** 즉 지도의 절반 이상은
  "무엇을 지을까"가 아니라 **"거기 뭐가 있는가"** 다. 이게 4층 구조의 요점이다.

### 16.2 티어 — 흡수합병의 대체

11 의 인접 흡수합병(같은 시설 여럿을 합쳐 배율 상승)은 격자 규칙이라 못 옮긴다.
**슬롯 하나 안에서 레벨 1→3 으로 올린다.** 배율 곡선은 **삼국지 11 참고값 1.2 / 1.5**
— 그대로 쓰지 말고 출처만 달아 둔다. 격자·인접이 사라지고 의도(집중 투자 보상)만 남는다.

### 16.3 신규 縣(§13 확장분)의 `level` — **문제가 아니다**

`level` 은 개별 사료값이 아니라 `county_level(jn)`(`build_han_world.py:472-483`)이 **소속 郡에서**
뽑는다. 郡만 알면 신규 縣도 기존과 같은 경로로 영현/장현을 받고 **소정착지 슬롯 1**을 갖는다.
새 규칙 0개. 남는 일은 §18 의 건물 배정 하나다.

## 20. 비-縣 노드 (관문 + 전장) — 신규 층은 **하나다**

> **2026-08-24 사용자 결정 — 「순수 전장은 별칭으로만」 안은 폐기됐다. 전장도 노드다.**
> 그리고 **노드 타입을 둘로 쪼개지 않는다.** 관문과 전장은 구조가 같다 —
> 간선 위의 점, 인구·내정·슬롯 없음, 전투만 발생. 차이는 **효과 유무 하나뿐**이다.
> **전장 = 효과 없는 관문.** 타입을 쪼개면 이후 모든 코드가 분기한다.
>
> 판정 규칙도 이 결정을 따라 갈라진다:
>
> | 대상 | `existsAt140` 판정 | 이유 |
> |---|---|---|
> | **자연 지형** (적벽·오장원·정군산·장판·기산·자오곡·진창도) | **불필요 — 시점 무관** | 208년에 유명해졌을 뿐 140년에도 거기 있었다 |
> | **인공 구조물** (관문·성·나루 시설) | **필수** | 축조 연도가 있다. 潼關은 建安, 夏口城은 223 |
>
> `historicity`(정사/연의전용/UNKNOWN) 축은 **양쪽 모두에 필수**다. 葭萌關 배제는 그대로 유효하다.


### 20.1 왜 노드인가 — 간선 속성이 아니라

`RawCity.path` 는 `Map<Int, String>` 이고 값은 표시용 이름이다. **간선에 속성을 달 자리가
없다.** 간선을 속성 가능한 모양으로 바꾸면 `CalcCityDistance`(PHP 바이트동일 포팅) 를 포함해
`path` 소비자 전부가 영향권에 든다. **노드로 두면 그래프 구조가 그대로다** — 관문도 城이고,
`path` 로 이웃과 이어지며, 이동·점령이 기존 규칙 그대로 돈다. **새 개념 0개.**

효과는 **"인접 縣에 적용"** 으로 준다 — `path.keys` 순회 한 줄. 참고 효과(토탈워 삼국 참고값,
**그대로 쓰지 말 것**): 교역 수입 +65%(인접), 적군 보급 -50, 공공질서 +10, 비축 상한 +120.

**공공질서는 새로 만들지 않는다** — `RawCity.security`(치안)가 이미 그 축이다.
토탈워의 **위신·만족도·교역 영향력·개혁·전문직 자원(장인/산업가/사업가)은 전부 뺀다.**
하나 넣으면 나머지가 딸려온다.

### 20.2 자료구조 — 관문도 `RawCity` 다

**새 타입을 만들지 마라.** 관문은 `level` 로 구분한다:

- che 의 `level 3 = 관`(관문)이 **이미 정의돼 있다**(`CityConst.kt:227`, `maxes["관"]`:
  pop 10000 / agri·comm·secu 100 / def·wall 1000). **han 에는 level 3 이 0개다** —
  **비어 있는 등급이 마침 '관'이다.**
- 따라서 관문 = `level 3`. `slotCount(3)` 은 §16.1 의 `else -> 0` 에 걸려 자동으로 슬롯 0.
  (슬롯 1을 주려면 `3 -> 1` 한 줄.)
- 소속은 기존 축 그대로: `HanJunIndex.junByCityId` 에 부모 縣의 郡을 넣는다. `region`(州)도 동일.
- 생성기에는 `SEAT_NAMES` 와 같은 형태의 **`GATES` 표**를 하나 더 둔다:
  `(이름, 한자, 부모 縣 한자, lon, lat, 근거, 140년존재)`.

```python
# tools/scenario/build_han_world.py — 제안
GATES = [
    ("함곡관", "函谷關", "穀城", 112.16587, 34.72051,
     "나무위키 河南尹 穀城縣 항목; 기원전 114 축조 명시", True),
    # …
]
```

`Proj`(§13.1)로 셀 좌표를 내고, `path` 는 **부모 縣 + 부모 縣의 이웃 중 관문이 실제로 막는

### 20.8 기존 그래프에 어떻게 더하나 — **간선 세분(subdivision)만 허용한다**

    assert b in conn[a], f"{name}: {a_ch}-{b_ch} 간선이 없다 — 이 항목은 뺀다"
    conn[a].discard(b); conn[b].discard(a)     # A—B 제거
    link(a, g); link(g, b)                      # A—G—B 삽입
```

**이 형태를 고른 이유 (다른 안을 버린 이유 포함):**

| 안 | 연결성 | 문제 |
|---|---|---|
| **세분 A—G—B** | **불변.** 차수 2로 끼우므로 컴포넌트 수·고립 수·`main_ratio` 가 전부 그대로 | 두 縣 사이 홉이 +1 된다 (아래) |
| 잎으로 매달기 A—G | 불변 | **관문**에는 못 쓴다 — 길 위에 없으면 막을 수가 없다. **전장에는 쓸 수 있다**(아래) |
| 근접 縣 자동 연결 | **깨진다** | #541 이 터진 방식. 금지 |
| 타일 재생성 | **깨진다** | #536. 금지 |

**세분의 진짜 비용 — 숨기지 않는다.** A—G—B 는 A↔B 거리를 1홉에서 2홉으로 늘린다.
`CalcCityDistance` 와 커맨드의 `cityDistanceLimit`(`SelectCityField.tsx:32-37`)이 그 위에서 돈다.
**90건을 끼우면 1783개 간선 중 90개(5.0%)의 길이가 두 배가 된다.** 이동·출병 밸런스가 조용히
바뀐다. → **관문에는 의도된 효과지만 전장에는 공짜 페널티다.** — **R32**

#### R32 — **완화하지 않는다. 사용자가 대가를 알고 수용했다**

> **2026-08-24 사용자 결정 — 「관문만 세분, 전장은 잎」 안은 폐기됐다. 90건 전부 세분한다.**

## 21. **가장 중요한 결정** — 건물과 기존 도시 스탯의 관계

### 21.1 결정: **`*_max`(상한)를 올린다.** 현재값도, 별도 축도 아니다

### 21.2 근거 — 셋 다 실측

**(1) `RawCity` 의 스탯은 이미 "현재값"이 아니라 "상한"이다.**
`CityConst.kt:79-84` 의 `raw.agriculture * 100` 이 `CityInitialDetail` 을 거쳐 DB `agri_max` 가 된다.
`V1__baseline.sql:43-44` 는 `agri` 와 `agri_max` 를 **따로** 갖고, 현재값은 내정 커맨드가 키운다
(`CommerceInvestment.kt:56·61·139`, `Presets.kt:136`). **상한과 현재값이 이미 분리돼 있고,
건물이 끼어들 자리는 상한 쪽이다.**

**(2) 런타임에 상한을 움직이는 선례가 이미 있다 — 증축/감축.**
`logic/src/main/kotlin/opensamguk/logic/actions/nation/CheJeungchuk.kt:69-77`:

```kotlin
// city: level+1; *_max += increments; current UNCHANGED (che_증축.php:173-181)
d.destCity = capital.copy(
    level = capital.level + 1,
    populationMax = capital.populationMax + popInc,
    agricultureMax = capital.agricultureMax + develInc, …
)
```

`CheGamchuk.kt:75-81` 이 그 역이다. **"상한을 올리고 현재값은 건드리지 않는다"는 패턴이
이미 검증된 채로 저장소에 있다.** 건물은 두 번째 사용자일 뿐이다.

**(3) 나머지 둘을 버린 이유**

| 안 | 버린 이유 |
|---|---|
| **현재값을 올린다** | 내정 커맨드가 하는 일을 건물이 공짜로 해 준다 → **"건물 짓고 내정 안 함"이 최적해**가 되어 내정이 죽는다. 게다가 `ProcessSemiAnnual.kt:86` 이 반기마다 현재값을 굴리고 `UpdateCitySupply.kt:161` 이 보급 끊기면 0.9배로 깎는다 → **건물 효과가 시간에 따라 증발한다.** 설명 불가능 |
| **별도 축이다** | 상한/현재값을 읽는 곳이 이미 넷이다: `AiWorldView.kt:198-200`(AI 도시 가치=합/최대합), `CheTalchwi.kt:264`(탈취량=`agri/agriMax` 비), `Presets.kt:557-558`, `ScenarioStartEventActions.kt:444·593`. **별도 축은 넷 전부가 배워야 하고, 상한은 한 곳도 안 고친다** |

### 21.3 부작용 — 숨기지 않는다

상한만 오르면 `agri / agri_max` 비가 즉시 떨어진다.

| 위치 | 무슨 일이 일어나나 |
