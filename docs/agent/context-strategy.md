# Context Strategy — 컨텍스트 유형별 사용 규칙

> 원칙(강의 자료 1주차): 에이전트 실패의 다수는 모델 실패가 아니라 컨텍스트 설계 실패다. 긴 컨텍스트일수록 중간 정보가 소실된다(needle in a haystack).

## 유형 1 — 코드 컨텍스트 · **이 저장소에서 실사용 중**

- 언제: 구현·리뷰·디버깅. 항상 "관련 파일 + 유사 구현 + 그 테스트"의 삼각형으로.
- 우선순위: code-review-graph MCP(`semantic_search_nodes`/`query_graph`/`get_impact_radius`)가 있으면 **Grep보다 먼저**(프로젝트 정책). 없으면 진입점(`architecture.md` §주요 진입점)에서 좁혀 들어간다.
- 읽는 양: 전체 파일 통독 대신 대상 심볼 ± 호출자/피호출자. 대규모 저장소이므로 루트 설정 → 진입점 → 대표 모듈 → 대표 테스트 순.
- 배제: 현재 갭과 무관한 모듈 소스를 "혹시 몰라서" 로드하지 않는다.
- 동반 검증: 읽은 코드에 대한 가정은 테스트 실행으로 확인(`verification.md`).

## 유형 2 — 파일·문서 컨텍스트 · **실사용 중**

- 언제: 규칙 확인, PHP 오라클 분석, 루프 재개.
- 우선순위: `.ai/task.md` → `docs/agent/README.md` 라우팅 결과 → PHP 원본(`legacy/devsam-core`의 정확한 path+line — 인용 필수) → 골든 픽스처.
- 읽는 양: 라우터가 지정한 문서만. PHP는 해당 명령/함수 범위만(파일 전체 아님).
- 배제: 과거 루프 원장·리서치 전체 로딩 금지. `.env*`·시크릿은 **읽지 않는다**.
- 동반 검증: 문서 주장(명령·경로)은 실행/존재 확인 후 신뢰. 오래된 `current-state.md`/`handoff.md`는 `git log`로 교차 검증.

## 유형 3 — 이미지 컨텍스트 · **실사용 중** (Playwright 스크린샷, `parity-shots/`)

- 언제: UI 패러티 비교, 시각 회귀 판단, 프로덕션 화면 재현.
- 우선순위: 실제 브라우저 캡처(Playwright/webapp-testing) > 기존 `parity-shots/` 비교본.
- 배제: 스크린샷 없이 UI를 "정상"으로 판단하지 않는다. 캡처 불가 환경이면 `채점대기`로 보고.
- 동반 검증: 시각 판단은 DOM/네트워크 관측과 함께.

## Needle in a Haystack 관리

강의 자료(1주차)의 건초더미 관리 3전략을 이 저장소의 실제 기제에 매핑한다. 아래 하위 절들이 각 전략의 실행 규칙이다.

| 전략 | 원리 | 이 저장소의 기제 |
|---|---|---|
| **① 주기적 요약 (MoM)** | 긴 대화의 결정·상태를 회의록처럼 압축해 파일로 고정 | `/os-checkpoint` → `.ai/current-state.md`·`.ai/handoff.md` 갱신 (시점: 아래 "작업 중" 절) |
| **② 헌법 + 메모리 GPS 고정** | 컨텍스트가 아무리 길어져도 최상위 규범과 핵심 사실은 매 세션 자동 주입되는 위치에 둔다 | `CLAUDE.md`(파리티 규율·하드 룰) + `.ai/task.md`(작업 계약) + `.ai/decisions.md`(ADR-LITE). 새 불변 사실은 대화가 아니라 이 파일들에 기록해야 소실되지 않는다 |
| **③ /clear 리셋** | 오염·포화된 컨텍스트는 요약 후 버리고 새로 시작 | 아래 "작업 전환" 절의 리셋 조건 + 리셋 전 `.ai/handoff.md` 필수 갱신 |

### 작업 시작

- `.ai/task.md` + 승인 결정만 우선 로드. 저장소 전체를 컨텍스트에 넣지 않는다.
- 관련 파일·유사 구현만 탐색(위 유형 1 규칙).

### 작업 중 — `.ai/current-state.md` 갱신 시점

계획 확정 후 · 주요 구현 완료 후 · 검증 실패 후 · 컨텍스트가 길어졌을 때 · 다른 에이전트로 넘기기 전. (Claude는 `/os-checkpoint` 커맨드가 이 갱신을 수행.)

### 작업 전환 — 새 세션/리셋 권장 조건

- 작업 성격 변경(예: 프론트 → 인프라/운영), 기능 구현 → 장애 대응 전환.
- 확정 규칙을 반복 누락하거나 이전 결정과 모순되는 행동이 나타날 때.
- 무관한 로그가 컨텍스트 대부분을 차지할 때.
- 리셋 전 반드시 `.ai/handoff.md` 갱신 — **장기 작업의 상태는 대화가 아니라 파일에 둔다.**

### 압축 원칙

- 남기는 것: 목표, 승인된 결정, 변경 파일, 검증 결과(실행/미실행 구분), 실패한 접근, 다음 행동, 미해결 위험.
- 버리는 것: 장황한 대화, 폐기된 아이디어의 세부, 중복 로그, 무관한 파일 내용, 재현 불가한 추측.
- 이 저장소의 압축 정본 형식 = 루프 LEDGER의 "바퀴" 행(가설/채점자/판정/원인 한 줄) — 상태 요약은 이 밀도를 따른다.
