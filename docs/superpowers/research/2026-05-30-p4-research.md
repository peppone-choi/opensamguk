## P4 Goal

P4 lifts the proven **per-general single-tick + monthly economy tick** framework of P0–P3 up to the **deterministic battle engine** — the war system that `che_출병` invokes from inside the per-turn command pipeline. The scope:

- The **TriggerCaller** registry + dispatch (ascending-priority bucket, `uniqueID` dedup, `raiseType` coexistence, stable insertion order within a bucket) — its `fire()` iteration order **IS the battle RNG draw order**.

- The **`processWar_NG` deterministic phase machine** (the exact RNG draw order: damage / wound / trigger / crit / avoid / magic; HP-ratio clamp; killed/dead; byte-exact phase logs) driven by ONE shared `RandUtil(LiteHashDrbg(warSeed))`.
- `WarUnitGeneral` (combat-power synthesis + `finishBattle` rounding) and `WarUnitCity` (HP = `def*10`, attack/defence = `(def+wall*9)/500+200`, year-scaled train/atmos, no own draws).
- `city.conflict` deterministic ordered-map (`arsort` tie-break, 선타/막타 ×1.05, 분쟁 log) and `getConquerNation` winner.
- `ConquerCity` full side-effect set (distinct conquest seed, collapse/survive/천도, winner tie-break — **all recorded as flush deltas, never inline DB write**).
- Battle **item + specialty (특기) trigger injection** via the same `iAction` contract P2 already ports.
- The **battleSim preview worker** (`j_simulate_battle.php`) reusing the engine, and the battle-generating command **`che_출병`** (NOT 급습/선전포고 — see Unit 8).

> **THE #1 PARITY RISK (design §13 #1 / §11 line 258):** `processWar_NG`'s draw-order byte-parity. Every battle/wound/trigger/crit/avoid/magic draw funnels through ONE `RandUtil(LiteHashDrbg(warSeed))` stream threaded into every `WarUnit`, so byte-for-byte parity reduces to **did the Kotlin port pull draws off this single stream in the identical ORDER**. A single conditional draw that appears/disappears (e.g. `computeWarPower`'s `warPower<100` floor, `tryWound`'s injury-amount draw, magic's success branch) shifts the entire downstream stream and silently desyncs the rest of the battle. The micro order (within one `TriggerCaller.fire()`) and the macro order (the phase loop wrapping the fires) must both be exact.

P4 **extends, never reshapes, the proven P0–P3 framework.** The following are already proven byte-faithfully and are directly reused, not rebuilt:

## Unit 1 — trigger-caller (TriggerCaller / ObjectTrigger — the draw-order registry)

### Summary
`TriggerCaller` is the trigger registry + dispatch that determines **battle draw order**. Because `processWar_NG` draws RNG inside trigger `action()` calls, **the iteration order of `TriggerCaller::fire()` IS the RNG draw order** — getting it wrong desyncs every battle. The ordering is a TWO-LEVEL stable sort: (1) outer key = integer `priority` (ascending; lower priority number fires FIRST), (2) inner = insertion order within a priority bucket, keyed by `uniqueID` for dedup. PHP arrays preserve insertion order within each priority bucket; `ksort` is run ONCE on the outer keys if input priorities are not monotonically non-decreasing. The dedup key = `priority + FQN + object-identity + raiseType` (all four must match to dedup). Two distinct skills at the SAME priority (e.g. `che_계략발동` and `che_계략실패`, both POST+300=40300) are distinct FQNs → both live in the bucket and fire in **constructor argument order** — PHP does NOT sort within a bucket, so Kotlin must use an insertion-ordered inner map (`LinkedHashMap`), NEVER a key-sorted one.

The canonical battle path is **constructor + `merge()`** (`General.php:920-934`), NOT `append()`. `append()` has a latent line-75 bucket-clobber bug but is unreachable in battle; core2026 "fixed" append to be additive — a faithful Kotlin port must replicate the path ACTUALLY USED and should NOT copy PHP's buggy append. `merge()` is a sorted-merge of two already-priority-sorted maps; within a shared priority bucket it does `array_merge(lhs, rhs)` → LHS uniqueIDs first (in order), then RHS appended. This is how `WarUnitTriggerCaller(base 7 triggers)->merge(crew)->merge(item)...` composes.

`uniqueID` format: base `ObjectTrigger` = `"{priority}_{FQN}_{objID}"`; `BaseWarUnitTrigger` OVERRIDES to append `_{raiseType}` → same skill class on same unit with DIFFERENT raiseType COEXIST (the "raiseType coexistence" rule — e.g. an item trigger `TYPE_ITEM=1` and a non-item version of the same class do not dedup). The canonical 7 base phase triggers (in constructor arg order, `General.php:920-928`): `che_필살시도`(PRE+120), `che_필살발동`(POST+400), `che_회피시도`(PRE+200), `che_회피발동`(POST+500), `che_계략시도`(PRE+300), `che_계략발동`(POST+300), `che_계략실패`(POST+300). After `ksort` the effective fire order: 필살시도(20120) → 회피시도(20200) → 계략시도(20300) → [계략발동, 계략실패](40300 in arg order) → 필살발동(40400) → 회피발동(40500). PRE-band "try" triggers draw their RNG first; POST-band "fire/fail" draw later; crew/item/buff triggers merge into these bands by their own priorities (merge order driven by the `getActionList` 9-source list).

### Pinned port_notes (RNG draw orders / rounding / tie-breaks)
- **Storage:** `LinkedHashMap<Int, LinkedHashMap<String, Trigger>>` — outer sorted ASCENDING by priority at fire time (TreeMap OR sort-on-fire), inner MUST be insertion-ordered (`LinkedHashMap`) to preserve same-priority arg order (계략발동 before 계략실패). NEVER a sorted/hashed inner map.

PHP `objID`=`spl_object_id` (per-process, non-reproducible) — use a STABLE per-unit id (`WarUnit.getUnitId()`, as core2026 does) and a stable class-name token. - **FQN token:** PHP uses `static::class` (full namespaced); core2026 uses short `constructor.name`. Choose ONE canonical token per skill class, apply uniformly, verify against golden.

- **`ksort` is a stable numeric sort on int priority keys; there is NO secondary comparator on ties.** Do not introduce one. Eager `TreeMap` or sort-on-fire are both fine if the sort is stable ascending.

## Unit 2 — oncalc-oppose (the cross-order stat fold + ~15 battle-stat keys)

### Summary
For each battle stat the value is folded TWICE in a fixed two-call sequence with **NO RNG draws inside the fold**: (1) `value = SELF.general.onCalcStat(self.general, statName, value, aux)`; then (2) `value = OPPOSE.general.onCalcOpposeStat(self.general, statName, value, aux)`. **BOTH calls pass the SAME first arg = the SELF (stat-owner) general**, never the opponent. `onCalcStat` is dispatched on the owner's General; `onCalcOpposeStat` is dispatched on the OPPONENT's General but still receives the owner General as `$general`. There is NO symmetric interleave — each `getComputedX()` computes ONE side's stat via this owner→oppose 2-step; the opponent computes its OWN stat in a separate call. The cross is: owner-side buffs (`onCalcStat`) THEN opponent-side counter-buffs (`onCalcOpposeStat`) layered on top.

Each fold is a plain left-fold over the EXACT 9-source `getActionList` order (IDENTICAL to P3's `getStatValue` pipeline — only the statName set differs). The fold draws NO RNG; it is pure arithmetic. RNG draws (`nextBool`/`nextRange`/`choice`) happen AFTER the fold returns, at the trial site. So byte-parity of the fold = correct stat ordering + correct PHP float arithmetic (`Util::round` only where applied later, in `calcDamage`).

**The ~15 battle stat keys:** `warAvoidRatio`, `warCriticalRatio`, `warMagicTrialProb`, `warMagicSuccessProb`, `warMagicSuccessDamage` (aux=magic name, MULTIPLICATIVE), `warMagicFailDamage`, `criticalDamageRange` (a `[min,max]` PAIR), `initWarPhase`, `bonusTrain`, `bonusAtmos`, `dex{armType}` (statName built as `'dex'.$crewType->armType`), `killRice`, `addDex`, plus non-battle `experience`/`dedication`. The keys that CROSS (self `onCalcStat` + oppose `onCalcOpposeStat`): warAvoidRatio, warCriticalRatio, warMagicTrialProb, warMagicSuccessProb, warMagicSuccessDamage, bonusTrain, bonusAtmos, dex{armType}. SINGLE-SIDED (`onCalcStat` only, NO oppose cross): `initWarPhase` (oppose not yet known at maxPhase calc), `criticalDamageRange` ([1.3,2.0] array), `killRice`.

**Exact trial draw orders at consuming sites:**
- AVOID (`getComputedAvoidRatio`): base = `crewType->avoid/100`; `*= getComputedTrain()/100` (runs the bonusTrain cross-fold); then warAvoidRatio cross-fold (onCalcStat then onCalcOpposeStat); THEN post-fold hard multiplier `if oppose armType==T_FOOTMAN: *= 0.75` (applied AFTER the fold, INVISIBLE to triggers).
- CRITICAL (`getComputedCriticalRatio`): base = `crewType->getCriticalRatio(general)` (T_CASTLE=0; mainstat by armType — WIZARD intel coef0.4, SIEGE leadership coef0.4, MISC avg-of-3 coef0.4, else strength coef0.5; `Util::valueFit(mainstat-65,0)*coef`; `min(50,ratio)/100`); then warCriticalRatio cross-fold.
- MAGIC (`che_계략시도`, PRE+300 — the most draw-dense site). STRICT order: (1) `magicTrialProb = intel/100 * crewType->magicCoef`; (2) warMagicTrialProb cross-fold; (3) if ≤0 return; (4) `phase==0 && rawIntel*3>=allStat ⇒ *=3` (AFTER fold); (5) **DRAW #1** `nextBool(magicTrialProb)` — fail⇒return; (6) `magicSuccessProb=0.7` then warMagicSuccessProb cross-fold; (7) **DRAW #2** `choice(array_keys(tableToCity|tableToGeneral))` — city `{급습,위보,혼란}` vs general `{위보,매복,반목,화계,혼란}`, key set chosen by `oppose instanceof WarUnitCity`; (8) warMagicSuccessDamage cross-fold on successDamage only (aux=$magic); (9) **DRAW #3** `nextBool(magicSuccessProb)` ⇒ 계략 (use successDamage) vs 계략실패 (use table failDamage, UN-folded). **DRAW ORDER WITHIN MAGIC = nextBool(trial) → choice(magic kind) → nextBool(success).**
- criticalDamage range (`WarUnit.php:437-447`): `range=[1.3,2.0]`; if WarUnitGeneral, `onCalcStat('criticalDamageRange')` (NO oppose); then `nextRange(...range)`.

## Unit 3 — processwar-phases (the processWar_NG deterministic phase machine — #1 PARITY RISK)

### Summary

## Unit 6 — city-conflict (the deterministic ordered-map + winner tie-break)

### Summary
The city-conflict map is a per-city JSON object `{nationID:accumulatedDead}` maintained by `WarUnitCity::addConflict()` (`:152-181`). On each siege aftermath, after both sides finishBattle, if the defender city took casualties OR the defender is a WarUnitCity, the city's `addConflict()` is called (`process_war.php:484-497`). **addConflict draws NO RNG — pure arithmetic + sort.** It sits OUTSIDE the RNG stream; correctness = byte-match of the stored conflict JSON and the `array_key_first` winner.

**EXACT addConflict algorithm:** (1) `conflict = Json::decode(getVar('conflict'))` (empty city `'{}'` → empty array, falsy); (2) `nationID = oppose->getNationVar('nation')` (the ATTACKER nation); (3) `dead = max(1, this->dead)`; (4) FIRST/LAST-HIT BONUS: `if(!conflict || getHP()==0) dead *= 1.05` (선타 = first nation to attack; 막타 = killing blow; turns dead into a FLOAT); (5) insert/accumulate: `if(!conflict)` → `[nationID=>dead]` (no arsort, single entry, newConflict=false); `elseif key_exists` → `+= dead; arsort` (newConflict=false); `else` (new nation, non-empty) → `= dead; arsort; newConflict=true` (triggers 분쟁 global log); (6) `updateVar('conflict', Json::encode(conflict))`.

**WINNER:** `getConquerNation = array_key_first(Json::decode(city.conflict))` — the FIRST key of the stored (already arsort-ordered) map = the nation with the highest accumulated weighted-dead, with PHP arsort's tie-break governing ties. `DeleteConflict($nation)` removes a destroyed/merged nation from every city's conflict map via unset (preserving remaining order; re-encoded WITHOUT re-sort).
