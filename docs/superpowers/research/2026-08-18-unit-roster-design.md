## 0. 무엇을 어디서 가져왔나

한 쪽을 베낀 것이 아니라 셋을 엮었다.

| 출처 | 가져온 것 | 가져오지 **않은** 것 |
| --- | --- | --- |
| devsam/core `che` 병종표 | armType 5종(보/궁/기/귀/차)과 그 상성 골격, 수치 4개(attack/defence/speed/avoid), cost/rice, `phaseSkillTrigger` 어휘 | 34행의 값 자체 — han 은 별도 세트다 |
| Total War: Three Kingdoms (namu.wiki) | **분해 축 하나** — 병종 = (무기 · 갑옷 · 방패) 조합이고 역할과 등급이 거기서 나온다는 발상 | 수치·이름·병종 목록. CC BY-NC-SA 2.0 KR 자료이고, 이 저장소는 이미 Koei-IP 심사 대기 중이다. IP 위험을 한 겹 더 얹지 않는다 |
| 사료 실측 (三國志·後漢書·資治通鑑·華陽國志) | 병종 이름·한자·출전·인용문·역할·게이팅 | 수치 — 사료에 수치는 없다 |

**파일은 하나다.** 한때 명부(`data/v2/unit-types.json`)·han 병종표·che 병종표가
갈려 있었는데, 그러면 진실이 둘이 된다. 지금은 `data/unitset/units.json` 하나다 — 사람이 적는
`authored` 필드(이름·한자·armType·등급·절·조성·게이팅·출전)와 빌더가 다시 쓰는 `generated`
필드(수치·계수·제약·info)를 `_meta` 가 명시한다. 빌더를 두 번 돌리면 같은 파일이 나온다.

## 1. 엔진을 건드리지 않는다

- **armType 을 늘리지 않는다.** armType id 는 모든 병종의 `attackCoef`/`defenceCoef` 맵의 **키**다. 6번째를 만들면 기존 34행 상성표를 전부 다시 써야 하고 그건 골든이 덮고 있다.
- **수치 필드를 늘리지 않는다.** TW3K 의 돌격보너스·사거리·탄약·사격속도는 들어갈 자리가 없다. 조성이 그 역할을 대신한다(아래 §2).
- **돌격 피해 반사는 새 메커니즘이 아니다.** 창병이 정면 돌격을 되받는 것은 `defenceCoef[기병] < 1` 한 줄이다. 모 0.6 · 삭 0.5 · 참마검 0.6 · 과 0.7 · 구겸도 0.7 · 극 0.8.
- 따라서 **패러티 영향 0**. `che` 표는 손대지 않았고, `ForbidRegions` 를 쓰는 기존 행은 없다.

## 2. 수치는 손으로 찍지 않는다

빌더가 조합에서 유도한다. 조합을 바꾸면 수치가 따라 움직인다 — 손으로 찍은 표는 균형이 어디서 깨졌는지 아무도 못 찾는다.

- **무기 28종 → 공격 + 공격계수 + 속도.** 타격(검·환수도·대도·부·철추) · 장병기(모·삭·극·과·구겸도·참마검·장모) · 투척(표창·투부) · 원거리(궁·강궁·단궁·노·연노·화시·독시·취전·목궁) · 공성(투석·충차·운제·정란) · 수송(치중).
  - 관통·타격(부·철추·노) → `attackCoef[보병]` 1.2~1.35, 대신 속도 −1
  - 장병기 → `defenceCoef[기병]` < 1 (아래 돌격 반사)
  - 걸어 끌어내리는 무기(과)·말을 베는 칼(참마검) → `attackCoef[기병]` 1.2~1.4
  - 독(취전·독시) → `attackCoef[보병]` 1.25~1.3 — 갑옷을 가리지 않는다
  - 무기 무게는 갑옷과 **따로** 센다. 가벼운 갑옷에 큰 칼도, 그 반대도 있다.
  - 양손 무기(구겸도·참마검·대도)와 장창(삭)은 방패를 들 수 없다 — 빌더가 조합 단계에서 거른다.
- **갑옷 → 방어 + 속도.** 의복 75 s8 → 강철갑 230 s6. 등갑 2종은 가볍지만 `defenceCoef[차병] × 1.5` (불에 두 배로 탄다).
- **방패 → 회피 + 대궁병 방어.** 없음 a0 / 소형 a15 / 중형 a10·궁병 0.8 / 대형 a5·궁병 0.65. 화살을 막을수록 몸이 굼뜬다.
- **기병** 은 speed +1, avoid +5. 활을 든 기병은 붙지 않고 도므로 avoid +10 을 더 받는다 — 치고빠지기가 곧 방어다.
- **cost/rice** = `round((공격+방어)/30) + 갑옷무게 + 기병2`, rice 는 기병 +1 / 차병 −5.

## 3. 게이팅

`ReqTech` 0/1000/2000/3000 사다리는 그대로 쓴다(민병→정예→최정예에 이미 대응한다). `ReqRegions` 의 **인자만** 새 맵의 州/郡 이름으로 바꾼다 — 메커니즘은 기존 그대로다.

새로 만든 것은 하나뿐이다.

```kotlin
data class ForbidRegions(val forbidRegions: List<String>) : UnitConstraint()
```

`ReqRegions` 의 거울이 아니다. 저쪽은 "나라가 그 땅을 가졌나"를 보고, 이쪽은 **"지금 이 부대가 어디 서 있나"** 를 본다. 없는 것을 뽑을 수 없다는 규칙이라 소유가 아니라 위치가 기준이어야 한다. 지역을 못 찾으면 막지 않는다(모르는 것을 금제로 바꾸지 않는다).

발동 근거: 三國志 卷30 倭人 「其地無牛、馬、虎、豹、羊、鵲」 — **왜 땅에는 말이 없다.** 邪馬壹國·奴國·投馬國 에 주둔한 부대는 기병 전 병종을 뽑지 못한다. 빌더가 `armType == 기병` 인 모든 행에 이 금제를 한 번에 건다(표에 흩뿌리지 않는다).

테스트: `logic/.../ForbidRegionsTest.kt` 2/2 green.

## 4. 조성 배정 — 역할 기본값 + 이름이 말하는 장비

71종에 (무기·갑옷·방패)를 붙이는 방법은 둘이다.

1. **역할 23종 → 조성 기본값.** `INFANTRY_GUARD` = 극·평철갑·중형방패, `CAVALRY_LIGHT` = 궁·경피갑,
   `NAVY_CAPITAL` = 모·중등갑·대형방패(누선은 뱃전에 방패벽을 세운다) …
2. **이름이 장비를 말하면 그쪽이 이긴다.** 板楯蠻의 板楯은 널방패고, 大戟士의 戟은 극이고,
   赤甲軍·白毦兵의 甲은 갑옷이고, 挹婁의 화살에는 독이 있다(「矢施毒，人中皆死」).
   連弩士는 연노, 彊弩는 노, 幽州突騎는 삭, 鐵騎·鐵車兵은 중철갑, 藤甲兵은 등갑이다.

빌더 표에는 아직 아무도 안 쓰는 무기가 남아 있다(참마검·철추·대도·취전·화시 …). 지우지 않았다 —
명부가 넓어지면 쓰인다. **쓰려고 병종을 지어내지는 않는다.**

## 6. 엔진 배선 (2026-08-19 완료)

`common/UnitCatalog` 이 세트 카탈로그다. `CityConstRegistry` 가 맵에 한 것과 같은 모양이되,
**한 가지가 다르다 — 세트 문자열을 실어나르지 않는다.**

세트마다 id 대역을 갈라 뒀기 때문이다(che 1000~1999 · han 2000~2999). 그래서 전투·표시처럼
"이 id 가 무슨 병종이냐"만 묻는 자리는 `UnitCatalog.byId(id)` 한 줄이면 되고, 세트를 알아야
하는 곳은 **뽑을 수 있는 병종을 나열할 때뿐**이다. 그 자리는 이미 `UnitSetTable` 이 `unitSet`
문자열을 받고 있었다. 60여 개 호출부에 세트를 꿰는 대신 id 대역 하나로 끝냈다.

- **che 는 JSON 을 읽지 않는다.** `UnitCatalog.all("che")` 는 `GameUnitConst` 를 그대로 위임한다.
  골든이 덮은 패러티 면을 로더에 태우면 파싱 하나로 조용히 어긋난다. JSON 의 che 행은
  `CheUnitSetExportTest` 가 지키는 사본이고, 런타임은 코틀린을 본다.
- `UnitSetTable.isSupported()` 가 세트 목록을 본다 — 이전엔 `"che"` 하나만 참이었다.
- `UnitSetTable.defaultCrewTypeId(set)` / `castleCrewTypeId(set)` 신설. `AutorunNationPolicy` 가
  상수 `DEFAULT_CREWTYPE`(1100)을 그대로 쓰다가 han 에서 NPE 나던 자리를 이걸로 바꿨다.
- 전투·표시 조회 `GameUnitConst.byId(` → `UnitCatalog.byId(` (logic 5파일 · game-api 3 · game-engine 3).
- 리소스는 gradle `processResources` 가 `data/unitset/units.json` 을 실어 나른다. 사본을 커밋하지 않는다.

**세트 선택은 시나리오가 한다.** `ScenarioImporter` 가 `map.unitSet` 을 월드 config 로 넘기고
`UnitSetTable.activeUnitSet(config, meta)` 가 그걸 읽는다. 아직 han 을 선언한 시나리오는 없다 —
배선은 끝났고 켜는 것은 시나리오 쪽 일이다.

**남은 것 하나.** `WarUnitCity` 의 성벽은 여전히 `CREWTYPE_CASTLE`(1000) 고정이다. han 성벽(2099)은
수치·계수가 che 성벽과 같게 만들어 둬서 지금은 결과가 같지만, 성벽을 세트마다 다르게 만들 거면
`WarUnitCity` 에 세트를 넘겨야 한다.

## 9. 총정리 (2026-08-19) — 두 세트를 한 파일로

`data/unitset/che.json` + `data/unitset/han.json` → **`data/unitset/units.json` 하나**.
파일이 둘이면 "우리 병종이 몇 종인가"에 답이 둘이 된다.

- `sets` — 세트 선언(`idRange` · `defaultCrewTypeId` · `castleCrewTypeId` · `frozen`).
  che 는 1000~1999 / 기본 1100 / 성벽 1000, han 은 2000~2999 / 기본 **2006(부곡 도병)** / 성벽 2099.
  han 의 기본 병종이 2100(유주돌기)이던 것을 고쳤다 — 기본값이 지역 전용 정예일 수는 없다.
- `equivalents` — che 34행 ↔ han 대응표. 맵을 갈아끼울 때 저장된 부대를 옮길 표이자,
  "che 의 이 병종은 han 에서 무엇인가"에 대한 답이다. 귀병 9종은 han 에서
  무격·방사·도사 3단으로 접혔으므로 7행은 `null` 로 **명시**한다(빠뜨린 것이 아니다).
- 세트 경계는 두 곳에서 지킨다 — 빌더의 `idRange` assert 와 `CheUnitSetExportTest`
  「세트 선언이 실제 행과 맞는다」.

**드리프트 게이트.** che 세트의 런타임 진실은 여전히 코틀린 `GameUnitConst` 다(골든이 덮은
패러티 면, 외부화는 `M-config` 마일스톤 이후). `CheUnitSetExportTest` 가 units.json 의 che 행을
코틀린과 필드 단위로 대조한다. 코틀린을 고쳤다면:

```bash
./gradlew :common:test --tests '*CheUnitSetExportTest*' -Dunitset.write=true
python3 tools/unitset/build_unitset.py --che common/build/che-export.json
```
