# han.json 고아 郡城 66건 사료 감사

- 대상: `infra/src/main/resources/map/han.json` 에서 `meta.jun == name` 이고 같은 `jun` 을 가진 城이 자기 하나뿐인 城 **66건**
- 성격: **조사 전용.** 코드·데이터 무수정, 커밋 없음.
- 사료 코퍼스: `data/corpus/` (1,271권, `historical-sources` 스킬 코퍼스). 인용은 파일 접두어로 표기 — `js-014` = 晉書 卷14 地理志上, `js-015` = 晉書 卷15 地理志下, `sgz-30` = 三國志 卷30 魏書 烏丸鮮卑東夷傳, `hhs-085/086` = 後漢書 東夷列傳/南蠻西南夷列傳, `dsfy-###` = 讀史方輿紀要, `sui-064` = 隋書 卷64.
- 데이터 근거: `data/map/junguozhi.json` (續漢書 郡國志 추출 106郡/1076縣), `data/map/han-places.json` (CHGIS V6 파생), `data/map/external-places.json` (CHGIS 밖 65지점), `tools/map/build_han_places.py`.

## 0. 먼저 정정해야 할 전제 두 개

작업 지시에 적힌 전제 두 가지가 저장소 데이터와 어긋난다. 판정 기준이 여기에 직접 걸리므로 먼저 적는다.

### (1) "시나리오 시작 연도 181~194" 는 사실이 아니다 — 실제는 **181~225**

`map.mapName == "han"` 인 시나리오는 15개이고 `startYear` 범위는 **181~225** 다 (`infra/src/main/resources/scenario/scenario_1*.json`):

| 시나리오 | startYear | 제목 |
|---|---|---|
| 1010 | 181 | 황건적의 난 |
| 1020 / 1021 | 187 | 반동탁연합 |
| 1120 | 188 | 백마장군의 위세 |
| 1030 | 191 | 군웅할거 |
| 1031 | 192 | 군웅축록 |
| 1040 | 193 | 황제는 허도로 |
| 1041 | 194 | 황제 원술 |
| 1050 | 197 | 관도대전 |
| 1060 | 199 | 원가의 분열 |
| 1070 | 204 | 적벽대전 |
| 1080 | 210 | 익주 공방전 |
| 1090 | 216 | 삼국정립 |
| 1100 | 222 | 칠종칠금 |
| 1110 | 225 | 출사표 |

즉 **한 장의 지도가 181년부터 225년까지를 모두 서빙한다.** 그러므로 "220년 曹魏 신설 郡" 이 무조건 역투영인 것이 아니다 — 1100(222)·1110(225) 에서는 오히려 정확하다. 반대로 그 郡들은 1010(181) 에서는 확실히 역투영이다.

**이 보고서가 채택한 판정 기준(명시):** 지도가 서빙하는 **가장 이른 시점 181년** 을 기준선으로 잡는다. 181년에 존재하지 않았으면 DROP 으로 분류하되, **각 행에 신설 연도와 "몇 번 시나리오부터 유효한지" 를 반드시 병기**한다. 임의로 자르지 않고 근거를 드러낸다. 다른 기준선(예: 220년)을 쓰면 판정이 뒤집히는 항목이 여럿이므로, 기준선 선택 자체가 정책 결정이며 이 보고서의 권한 밖이다.

### (2) 근본 원인 — 지도 빌더가 **220년**으로 잘라 만들어졌다

`tools/map/build_han_places.py:72`

```python
ap.add_argument('--year', type=int, default=220)
```

`build_han_places.py:87` 과 `:118` 이 이 `--year` 로 CHGIS `BEG_YR`/`END_YR` 를 필터한다. 즉 **han 지도의 시간 기준선은 처음부터 220년**이었다. 이 66건 중 曹魏/蜀漢/吳 신설 郡이 그대로 통과한 건 버그가 아니라 설정값의 귀결이다.

CHGIS `begYr` 기준으로 `--year 181` 이면 아래 22개 郡 후보 중 **19개가 자동으로 빠진다**. 남는 건 長樂郡(begYr 184), 新成侯國(begYr −7), 帶方郡(external-places 는 `begYr −9999` 라 연도 필터가 무효) 셋뿐이다.

## 1. 요약

| 판정 | 건수 |
|---|---|
| **KEEP-정규** (續漢書 郡國志 소재 後漢 郡 + 後漢書 본문이 後漢 郡으로 명기한 1건) | **14** |
| **KEEP-이민족** (郡 규약 밖 이민족·외국 거점) | **30** |
| **DROP-역투영** (181년 기준 시기 밖) | **20** |
| **UNKNOWN** (사료 상충 또는 정사 근거 0) | **2** |
| 합계 | **66** |

부가 사실:
- KEEP-정규 13건이 縣 0인 이유는 단일 원인이다 — `data/map/han-places.json` 에 그 郡의 **縣 좌표가 한 점도 없고**, `data/map/external-places.json` 의 郡 단위 대표점 하나만 있다. 확인: `膚施·離石·善無·臨戎·朝鮮·高句驪·襄平·龍編·胥浦·朱吾` 전부 `han-places.json` 에 부재.
- 그래서 이 13건은 **삭제 대상이 아니라 개명 대상**이다. 규약대로면 `요동군 → 양평`, `낙랑군 → 조선`, `현도군 → 고구려`, `교지군 → 용편`, `구진군 → 서포`, `일남군 → 주오`, `상군 → 부시`, `삭방군 → 임융`, `정양군 → 선무`, `서하군 → 이석` 이 되어야 한다. (屬國 3건 — 張掖·龜茲·遼東屬國 — 은 屬國都尉라 治所縣 개념 자체가 없어 예외다. `junguozhi.json` 에서도 이 셋만 `seat: null`, `counties: []` 다.)
- DROP 20건 중 **13건은 이미 지도에 실재하는 城과 같은 땅**이다(순수 중복). 나머지 7건은 그 자리의 後漢 縣이 지도에서 통째로 빠져 있어, 지우면 구멍이 생긴다 — 지우기보다 **後漢 縣 이름으로 개명**하는 편이 규약에 맞다.

## 6. 검증하지 못한 것 (정직하게)

1. **三國史記가 코퍼스에 없다.** 우산국·실직국·압독국·소문국·졸본·국내성·고령가야·대가야·성산가야 **9건**의 출처를 이 감사로 확인하지 못했다. 표에 `‡` 로 표시했다. 郡이 아니라는 분류는 확실하지만 사료 인용은 비어 있다.
2. **가야 3종의 명칭 시대착오를 판정하지 않았다.** `伽耶`/`加耶` 는 코퍼스 전권 0건이고 3세기 사료의 弁辰 12국 명칭 체계와 다르다. '5가야' 명명이 三國遺事(1281) 계열이라는 점은 이 코퍼스로 확증하지 못했으므로 DROP 처리하지 않고 경고만 달았다.
3. **西陵郡·廬陵郡을 못 갈랐다** (§4). 코퍼스 밖 사료(水經注·太平寰宇記·宋書 州郡志)와 CHGIS V6 원 dbf 출전 필드를 보지 못했다.
4. **CHGIS begYr 와 정사가 어긋나는 항목을 조정하지 않았다.** 固陵郡(CHGIS 194 vs 晉書 建安21년/216), 長樂郡(CHGIS 184 vs 讀史方輿紀要 晉 太康5년/284), 涪陵郡(CHGIS 216 vs 晉書 建安6년/201). 사료를 우선해 표기했고 CHGIS 값도 함께 남겼다.
5. **`data/map/junguozhi.json` 자체의 추출 오류를 전수 검사하지 않았다.** 遼東郡은 `checksum: FAIL` 이고 seat 이 `無` 로 잘못 잡혔다(襄平 유실). 西河郡 seat 은 `平`, 定襄郡 屬縣은 `善無` 1개, 巴郡의 `涪陵` 은 `涪` 로 잘렸다. 다른 郡에도 같은 계열 오류가 얼마나 더 있는지는 세지 않았다.
6. **`--year 181` 로 실제 재빌드해 보지 않았다.** §0(2)의 "19개가 빠진다"는 CHGIS `begYr` 값을 손으로 대조한 추정이며 빌더를 돌린 결과가 아니다(조사 전용 지시에 따라 실행하지 않았다).
7. **시나리오별 지도 분기 여부를 확인하지 않았다.** 181~225를 한 장으로 서빙하는 현재 구조에서 §3의 판정을 어느 기준선으로 확정할지는 정책 결정이며, 이 보고서는 기준선을 181로 놓았다고 명시했을 뿐 결정하지 않았다.
8. **哀牢(569)의 배치 타당성을 판정하지 않았다.** 後漢書 卷2 「十二年(69)…於是置永昌郡」에 따라 69년에 이미 郡으로 편입됐으므로, 이민족 거점으로 따로 두는 것은 사료가 아니라 게임 설계의 선택이다.
