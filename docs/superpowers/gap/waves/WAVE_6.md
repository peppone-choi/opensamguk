## foundation-first 빌드 순서

Tier-0 공유 확장점(여러 family가 consume) → consumer 순. **같은 파일을 두 family가 co-widen하면 안 됨**(merge conflict). 이 wave의 cross-area 공유 아티팩트는 `common/.../wire/TurnDaemonCommand.kt`(신규 변형) + `app/game-api/.../reserve/CommandWireMapper.kt`(intakeCodes/toCommand) + `app/game-engine/.../run/TurnDaemonCommandDispatcher.kt`(분기) 세 파일이며, **6a(Message)·6c(Auction Open)가 모두 이 셋을 넓힌다 → 반드시 순차(creator-then-consumer)**.

- **Tier-0 (foundation, 순차·creator-first):**
  - **F1** `common/.../wire/TurnDaemonCommand.kt` — `SendMessage`(personal/national/diplomacy mailbox+text) + `AuctionOpenResource`(buy/sell rice: amount/closeTurnCnt/startBidAmount/finishBidAmount) + `AuctionOpenUnique`(itemID/amount) 신규 변형 3종을 **한 번에** 추가. 6a/6c가 consume. **wire 변형은 단일 PR에서만 넓히고 그 뒤 핸들러/매퍼는 disjoint하게 병렬.**
  - **F2** `MessageStore` 엔진 구현(현재 logic interface만 존재; engine flush 측 구현 어댑터) + 엔진 `SendMessageHandler`/`DeleteMessageHandler` 신규 핸들러 — F1의 `SendMessage` 변형을 소비, `ChangeRecorder.recordMessageInsert/Invalidate`(완료 #2) + logic `sendMessage`(완료 #2)로 부수효과 적용. `VoteHandler`/`BoardHandler` per-run 주입 패턴을 미러.
  - **F3** `:logic` `auction/AuctionOpenResource.kt` + `AuctionOpenUnique.kt` — `AuctionBasicResource.php:20-93 openResourceAuction`(검증 5종 순서 + minimumRes 가드 + prevAuction 가드 + closeDate 산출 + host 자원 차감) / `AuctionUniqueItem.php openItemAuction` faithful 포팅(기존 `AuctionBase` consume; co-widen 금지 — 신규 파일).
  - **F4** `infra/.../ReservedTurnRepository.kt`에 `pushGeneralTurn(generalId, turnCnt)` + `repeatGeneralTurn(generalId, turnCnt)` 링-회전 메서드 추가(`func_command.php:31-107` UPDATE 시맨틱). 6e REST가 consume.
- **Tier-1 (consumer, F1~F4 이후 병렬, disjoint):**
  - 6a Message REST + handler 배선(F1·F2 consume) · 6c Auction Open REST + handler(F1·F3 consume) · 6b Vote REST(완료 intake 위 adapter, 공유파일 무관) · 6e Command queue REST(F4 consume) · 6d Join/BuildNationCandidate REST + FE 진입 · 6f NPC select-pool(독립, 신규 스키마 — OQ 참조).

## 병렬화 그룹 (disjoint worktree family)

cross-area 공유 아티팩트 3파일 — `common/.../wire/TurnDaemonCommand.kt`(T1) · `CommandWireMapper.kt`(T4) · `TurnDaemonCommandDispatcher.kt`(T4·T13). 동일 파일 co-widen 금지 → 다음 직렬화:

- **Group 0 (foundation, 순차):** **T1**(wire 변형 3종, 단독 PR) → 그 다음 핸들러/logic/repo는 **disjoint 병렬**: {T2,T3}(message handler, 신규 파일) · {T7}(auction open logic+handler, 신규 파일) · {T10}(ReservedTurnRepository push/repeat) 동시. 마지막 **T4**(CommandWireMapper + Dispatcher — T2/T3/T7 핸들러 존재 후 단일 배선 task) · **T13 디스패처 분기**는 T4와 같은 Dispatcher 파일 → **T4와 순차**(또는 T4에 합침).
- **Group A (Message surface):** T5 → T6. (game-api MessageController + FE mailbox — disjoint. T4 이후.)
- **Group B (Auction Open surface):** T8. (AuctionController open 메서드 + FE auction tab — T7·T4 이후. AuctionController는 read 메서드만 있던 기존 파일 → open 메서드 추가는 단일 family.)
- **Group C (Vote write surface):** T9. (**공유파일 무관 — 즉시 병렬 가능.** intake 완료 위 얇은 REST, VoteController write 메서드 + FE vote submit.)
- **Group D (Queue mgmt):** T10 → T11 → T12. (ReservedTurnRepository → CommandQueueController(신규 파일) → FE. T12는 WAVE 5 T5 편집기 의존.)
- **Group E (Founding/Join entry):** T13 → T14. (FoundingController/JoinController 신규 파일 + FE join 페이지. T4 디스패처 이후.)
- **Group F (NPC select-pool):** T15. (신규 스키마 + NpcSelectController — **독립, OQ-2 reachability 결정 의존**. 다른 family와 disjoint.)

→ **disjoint 병렬 family 수 = 6** (A=Message, B=Auction Open, C=Vote write, D=Queue, E=Founding/Join, F=NPC select). Group 0(T1 wire + foundation 핸들러/logic/repo)는 A·B·E의 선행 foundation; C·D·F는 Group 0 wire 의존도가 없거나(C·D) 자체 독립(F).

## 패러티 주의점

- **RNG (draw 순서/개수/args).** ① `BuildNationCandidate.php:82-87`은 전용 RNG(`simpleSerialize(hiddenSeed,'BuildNationCandidate',generalID)`)로 `che_거병->run($rng)`를 돌린다 — 거병 resolver의 draw 시퀀스는 `CheGeobyeong`가 grand truth(완료 #5). 신규 REST는 **추가 draw를 발생시키지 말 것**(typed publish만). ② `j_get_select_npc_token.php:113-127`은 `'SelectNPCToken',userID,now` 시드 + `choiceUsingWeight(pow(allStat,1.5))` 가중 추첨 — now가 시드에 들어가 비결정적, 골든 capture 시 시각 고정 필요(OQ-2). ③ Vote 추첨(voteUnique)은 완료·green — **재구현 금지.**
- **Rounding.** `j_get_select_npc_token.php:132 Util::round(pow($turnterm,0.672)*8)` = half-away → `PhpRound`. Auction Open의 `amount*0.5`/`*2`/`*1.1` 비교는 정수-스케일 부등식(반올림 아님) — PHP 비교 그대로.
- **한국어 로그 byte-parity.** `j_select_picked_general.php:148-151`/`j_update_picked_general.php:143-144`의 등장/변경 로그(`<Y>{name}</>, <G>{city}</>에서 등장` + JosaUtil 이/로)는 byte-정확 — 6f가 도달 가능하면 `ActionLogger` 경로 미러 필요(OQ-2). SendMessage/Auction Open launch는 로그 문자열을 생성하지 않음(메시지 본문/경매 detail 문자열은 잔여 — `{hostResName} {amount} 경매` `AuctionBasicResource.php:74`는 detail 필드, 로그 아님).
- **flush-delta (created/dirty/deleted).** SendMessage → `recordMessageInsert`(receiver 먼저, sender 나중 — append-additive 순서가 패러티, `JdbcFlushExecutor.kt:920` 보장). DeleteMessage → `recordMessageInvalidate` + `req_del_msg` overwrite는 신규 INSERT. Auction Open → 경매 채널 INSERT + host 자원 `diffGeneral`. **인라인 DB write 금지** — 전부 ChangeRecorder 델타.
- **insertion-order (LinkedHashMap).** `MessageTarget.toArray`(`MessageTarget.php:98-107`)의 6필드(id/name/nation_id/nation/color/icon) 순서 + message 본문 jsonb(`src`/`dest`/`text`/`option`) 순서는 `sendRaw`(`Message.php:310-315`) 순서 그대로. Auction Open `AuctionInfoDetail` 필드 순서(`AuctionBasicResource.php:73-82`)도 보존.
- **one-daemon-write-rule.** 모든 6a/6c 신규 mutation은 game-api가 typed `TurnDaemonCommand`를 publish하고 데몬이 핸들러에서 `ChangeRecorder`로 적용(완료 #2/#6 패턴). game-api는 **publish만** — JPA write 금지. 6e의 `ReservedTurnRepository.push/repeat`는 `:infra` 공유 JDBC 클래스(데몬도 game-api도 호출, `engine.boot`/intake 패턴과 동일 sanctioned)이며 EntityManager write가 아님 → 규칙 무위반.

## 오픈 질문

- **OQ-1 (6d Join scope).** `Join.php`는 21KB(inherit 포인트 차감 + InheritancePointManager + 능력치/특기/도시/턴타임존 선택 + member dup 가드)로 매우 크다. scenario_1010은 gateway 로비 인증(F0) 기반이고 in-game Join은 게이트웨이 OAuth divergence와 겹친다. **T14를 (a) full Join 포팅, (b) 거병/possession 진입만 우선하고 Join은 백로그, 중 무엇으로?** inherit 포인트 시스템(P6 inheritance enum)이 Join을 어디까지 지원하는지 코드 확인 필요. 결정 전 골든 capture 여부 미정.
- **OQ-2 (6f reachability).** `select_npc_token`/`select_pool` 테이블은 현재 Kotlin 스키마에 부재(V1/V7에 없음) + scenario_1010은 npcmode 미설정으로 보임. **6f를 (a) 신규 스키마+컨트롤러 full 포팅, (b) reachability 게이트로 quarantine(scenario_1010 도달 불가 증명 + 백로그), 중 무엇으로?** PossessionController(`POST /api/general/claim`)가 빙의의 단순 버전을 이미 커버 — 중복도 검토 필요.
- **OQ-3 (6d BuildNationCandidate 골든).** `BuildNationCandidate`는 거병 RNG를 돌린다 — `CheGeobyeong`의 draw가 이미 golden green(`GeobyeongTest`)이므로 BuildNationCandidate-전용 시드(`'BuildNationCandidate',generalID`)로 추가 골든이 필요한가, 아니면 거병 골든 재사용으로 충분한가? (시드 컴포넌트만 다르고 draw 시퀀스는 동일 resolver.)
- **OQ-4 (6e bulk vs WAVE 5).** WAVE 5 T1이 `CommandReserveService`에 nation_turn 경로를 추가했다. 6e `ReserveBulkCommand`는 general ring(`Command/`)과 chief ring(`NationCommand/`) 양쪽에 존재 — W6 T11은 general ring bulk만 다루고 chief ring bulk는 WAVE 5 편집기(T5)에 위임하나? 아니면 양쪽 통합?
- **OQ-5 (WAVE 3e Auction DTO 선후).** 6c FE의 bidList/logs read 보강은 WAVE 3e(Auction bidder/highestBid/host/remainPoint/logs DTO)에 의존. WAVE 3e가 먼저 머지되어야 6c FE가 완전한 read를 렌더한다 — W6 T8 FE는 3e 완료를 전제로 하나, 아니면 thin read로 먼저 출시하고 3e 후 보강하나?
- **OQ-6 (Message precheck).** SendMessage는 PHP에서 precheck(차단/penalty/limit) 후 launch한다 — 6a는 game-api에서 precheck 없이 typed publish(intake)하고 데몬 핸들러가 게이트(`VoteHandler` 패턴)하나, 아니면 game-api precheck를 추가하나? penalty/blockLevel/limit 상태가 daemon world에 실려 있는지 확인 필요.
