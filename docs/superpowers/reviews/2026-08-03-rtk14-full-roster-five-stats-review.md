# Review: RTK14 full roster, lifecycle, and five-stat surfaces

Scope: RTK14 source lifecycle-repair (V38), claim-request (V37), importer, and possession remediation, plus the Docker PR #25 Compose contract
Verdict: cleared

This cleared review covers the deep repair-migration remediation review only. It is not a final full gate, PR-review sequence, merge, deployment, reseed, or live verification.

Migration layout note: findings below are recorded in the order they were raised, and several were originally resolved by extending `V26__npc_lifecycle_phase_units.kt`. That approach was abandoned. `V26__npc_lifecycle_phase_units.kt` and `V26NpcLifecycleMigrationTest.kt` are now reverted byte-for-byte to `origin/main`, and every RTK14 lifecycle repair lives in one new world-scoped migration, `V38__rtk14_npc_lifecycle_repair.kt` (test: `V38Rtk14NpcLifecycleRepairMigrationTest.kt`), which runs on every world. The claim-request migration was renumbered `V36__general_owner_claim_request.sql` → `V37__general_owner_claim_request.sql`, because `origin/main` already ships `V36__diplomacy_casualties.sql` and two V36s make Flyway fail with a duplicate version. Read every "V26 now …" resolution below as "V38 now …".

## Findings and resolution

- The first review found exhausted duplicate-name candidates falling back to implicit politics/charm 50/50. The builder now requires exact runtime-identity collision overrides and fails closed when any legacy-only row lacks reviewed values.
- The first review found matched lifecycle changes could shift later legacy `InitScenario` draws. Tuple index 24 now records pre-enrichment activity, old-active rows phantom-consume legacy build draws, and newly active or appended rows use `InitScenarioRtk14`.
- The second review found 25-slot legacy-only rows were incorrectly receiving null `rtk14_*` provenance. Metadata now requires a non-null RTK14 officer number, with an end-to-end negative regression.
- PR review found the shared `general_neutral` tuple was decoded with direct-action offsets. Neutral deferred officers now use the importer layout, including birth/death at indices 9/10, and malformed nullable year scalars fail closed.
- PR review found the lifecycle migration could lose an underage officer after RTK14 enrichment rewrote the tuple birth year. The repair (now V38) keeps exact birth matching first and uses a unique source-provenanced identity fallback only for the pending pre-repair upgrade case.
- PR review found NPC possession redirected after intake acknowledgement instead of daemon completion. The UI now waits for the terminal command result and preserves the selection screen on denial, timeout, or missing request ID.
- PR review found the tuple-24 RNG marker was decoded ad hoc and RTK14 additions outside `general` could be silently dropped. The marker is now typed, and `general_ex`/`general_neutral` additions fail closed to preserve initialization order.
- PR review also hardened archive-only scenario exclusion and secret-step tracing checks. Claims that legacy politics/charm defaults should be removed and that the mocked `GameChrome` test leaked API calls were rejected after verifying the persisted V16 defaults and complete API-child mocks.
- A later exact-HEAD review found the lifecycle migration still scheduled source-enriched rows at `birth + 14` and the possession retry path mishandled an idempotent success without a request id. V38 now uses `appearanceYear ?: birth + adultAge`; `CharacterClaim` completes the documented `AlreadyOwnedBySelf` success without polling while preserving every `result:false` denial.
- The next exact-HEAD review found that the lifecycle migration's database selector still excluded a stored-adult row whose reviewed RTK tuple moved appearance into the future. V38 now unions the original underage cohort with adult rows only when tuple index 24 proves they were legacy-active, explicit appearance is future, and identity matching is safe; ambiguous same-name adult rows remain untouched.
- The following exact-HEAD review found `seedGenerals(false)` dropped workbook-enriched officers that remained in `general_ex`. Source-provenanced rows are now selected by non-null officer number independently of the legacy extension flag, while ordinary legacy extensions remain filtered; a 1,000-ID split-section regression passes.
- The same review proved that account ownership was persisted before daemon completion, so a retry could turn terminal denial or timeout into a no-request-id false success. The claim-request migration — `V37__general_owner_claim_request.sql` after the renumber — stores the original `claim_request_id`; retries and reloads reuse that request without republishing, matching terminal denial conditionally releases only its provisional reservation, and correlated ownership is finalized only at `npc_state=1` with matching `general.user_id`. Pre-claim-request null-id finalized ownership remains compatible only outside the claimable `npc_state=2` pool.
- The next review found that a source-retained `general_ex` row still consumed disabled-extension build draws from legacy `InitScenario`, shifting later neutral officers. It now keeps legacy affinity/ego replay but routes build draws through `InitScenarioRtk14`; a four-quadrant integration test proves downstream neutral stability.
- The same review found reload could hide a terminally denied provisional claim before the only POST cleanup path ran. Claimable GET now reconciles only an exact durable world/request/type/general denial through the conditional reservation delete, returns the reason with a new candidate token, and never republishes a command.
- The review also found the lifecycle migration used classpath-only lifecycle data and could silently skip external-only or overriding scenarios. A shared resolver now enforces external-over-classpath precedence for seeding and for the repair migration; selected external read/parse failures propagate, V38 resolves before DML through Flyway configuration and fails closed, and every source Flyway app plus canonical per-server game-api/engine receives the same read-only scenario directory.
- The complete historical review feed also exposed a deploy-only conflict between the source roster's fixed 678-row test and pre-build RTK14 materialization. The workflow now runs the source JVM gate first, then materializes the 1,000-row roster for image builds; static ordering and source-number exact-once contracts cover both phases.
- The exact prior source HEAD `725195fea29b3434cc358e3d262c6c440830dab7` review found P1: V26 had no forward repair for worlds that had already recorded the affected lifecycle state. That is resolved by moving the entire repair out of V26 into a new world-scoped migration, `V38__rtk14_npc_lifecycle_repair.kt`, and reverting V26 and its test to `origin/main`. A database that already recorded V26 in `flyway_schema_history` never re-runs it, so extending V26 could not reach upgraded worlds; and on a fresh database Flyway runs before `ScenarioSeedRunner` (an `ApplicationRunner`), so `world_state` is empty and V26 returns immediately, making the extension unreachable on new worlds too. V38, which no world has recorded yet, is what makes already-migrated worlds and freshly seeded worlds converge on the same final state.
- CodeRabbit found the migration could silently choose among ambiguous future database rows. That ambiguity is now rejected in V38, which fails closed for duplicate future-appearance identities; no V26 change is involved.
- CodeRabbit found deferred identity was name-only. V38 now uses the actual action identity `name[2]` plus `nation[4]`; it excludes `rtk14Added`, uses external-over-classpath resolution, and applies universal strict-shape checks before it rewrites anything.
- V38 rewrites only verified historical V26-scheduled events, splits verified grouped events by explicit appearance year, preserves unrelated or near-shaped grouped content byte-for-byte, and fails closed when an identity cannot be made unique.
- CodeRabbit found the importer silently dropped a lifecycle-invalid tuple. Importer validation now rejects `appearanceYear > deathYear` before seeding.
- CodeRabbit found possession cleanup hid a conditional delete inside `takeIf`. The explicit branch now returns a denial reason only after the matching provisional reservation is deleted.
- Docker PR #25 review found an indentation scan too weak to prove the runtime mount and a daemon-host-relative-path defect. The candidate branch now defaults the source side through `COMPOSE_HOST_DIR` and asserts rendered Compose JSON for exactly the game-api/game-engine read-only mounts.
