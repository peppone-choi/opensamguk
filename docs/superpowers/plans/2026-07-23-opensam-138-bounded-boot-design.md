The implementation was then reconciled back to this design: `WorldSnapshotLoader` stops retaining `statisticRows`, `nationHistory`, `generalHistory`, and `globalLogs` in `TurnWorldState.meta`, removes stale copies of those keys from persisted `world_state.meta` at boot, and serves the cold data through bounded on-demand readers.

## 0. Why this ticket is picked over an "OPENSAM-137 residual"

`OPENSAM-137`'s own design and review artifacts explicitly hand off to this ticket: the catalog marks `loadStatisticRows`, `loadNationHistory`, `loadGeneralHistory`, `loadGlobalLogs`, and `loadInheritancePoints` as `LEGACY_FULL_SCAN_PENDING_S5_T2` and its review's residual caveats say verbatim *"S5-T2 still owns bounded retention/removal for the cataloged `LEGACY_FULL_SCAN_PENDING_S5_T2` boot scans."* The one deferred piece of S5-T1 itself — activating the `registerAuction()` phase-hot prefetch cutover — is explicitly gated on `ARCH-S1-T3`/`#271`, which is **still open**, so there is nothing implementable left in the S5-T1 activation lane today. S5-T2 has no such external gate. This confirms the task's default recommendation.

## A. `WorldSnapshotLoader` methods to stop full-scanning

All five methods below live in `app/game-engine/src/main/kotlin/opensamguk/engine/boot/WorldSnapshotLoader.kt` and are cataloged `QUERY_ONLY_COLD` / `LEGACY_FULL_SCAN_PENDING_S5_T2` in `HotColdCatalog.snapshotAccesses`. None carry a `LIMIT` or a keyset predicate today; each scans an entire relation (or an entire cross-referenced KV namespace) once at boot and stores the full result in `TurnWorldState.meta`, which is part of `InMemoryTurnWorld`'s resident state for the rest of the process lifetime — this is the actual heap-retention problem the GH AC targets, not merely "a slow boot query."

### A.1 `loadRankValues` — same fix, different starting classification

`loadRankValues` (`:492-498`, `rank_data`, unbounded `ORDER BY general_id, id`) is currently cataloged `ALWAYS_HOT`, not `LEGACY_FULL_SCAN_PENDING_S5_T2` — because its output is genuinely resident (merged into every `TurnGeneral.meta` and read every tick via `general.meta[type]`, e.g. `WorldActionContext.topRankString()`/`effectiveRankValue()`, `AiTurnAdapter`'s `getRankVar`). It should **stay** `ALWAYS_HOT`. But its SQL is exactly the same unscoped-full-table-scan shape as the five methods above. Since the current V32 schema makes `rank_data.world_id` required, the implementation scopes the hot cohort with `WHERE world_id = ? ORDER BY general_id, id`.

### A.2 Why "omit from daemon meta" (not "bounded window in meta" or "game-api cold-only") for #1–#4

Three replacement shapes were considered per the task prompt:
- **Omit from daemon meta entirely, read on demand** — chosen for #1–#4. Each of these four is read at a specific, identifiable trigger point (emperor coronation, general death, nation fall, monthly yearbook), never inside the RNG-draw/entity-iteration loop, and never for "all entities" at once — only for the one entity or one time-window the trigger concerns. Keeping any window of it resident buys nothing; the bounded query at the trigger point is cheaper than maintaining a stale cache that would need its own invalidation story.
- **Bounded window resident in meta** — this is the right shape for #5/`loadInheritancePoints` (and the already-`ALWAYS_HOT` `loadRankValues`), because their consumer (`MergeInheritPointRank`) needs the **whole current set** at once, not one key — but "whole current set" is bounded by live-owner-count, so the fix is narrowing the SQL predicate, not touching residency.
- **game-api cold-only (delete the daemon read path, point callers at the existing read-side repositories)** — not applicable here: game-api's `HistoryReadRepository`/`GeneralTurnReadRepository`/`LogFeedReadRepository` are **JPA** repositories in a different module; the daemon's one-write-rule architecture keeps game-engine JDBC-only end to end (`JdbcFlushExecutor`, never `EntityManager`). The design instead **mirrors** those repositories' query shape as new bounded JDBC helper methods inside `infra`/`game-engine`, so the same predicate/ordering contract holds without crossing the JPA/JDBC module boundary the write path is architecture-tested against.

### B.1 Ordering parity requirement

The boot-scan versions of `nationHistory`/`generalHistory` are ordered `nation_id ASC, id DESC` / `general_id ASC, id DESC`, then indexed by id at read time — so the *effective* per-entity order actually consumed is `id DESC` (most-recent-first) for that one entity's list. The replacement exact-key query (`WHERE nation_id = ? ORDER BY id DESC`) must reproduce that same intra-entity order, and `DatabaseHooks`'s existing `currentHistory + persistedHistory.orEmpty()` concatenation order (pending-this-run first, then persisted) must be preserved verbatim by whatever new seam replaces it in `JdbcFlushExecutor`. Any reordering here is a silent parity break in the `ng_old_generals`/`ng_old_nations` archived `history` JSON field — verify with the existing archive-row golden/IT coverage, not just a new unit test.

### B.2 `inheritancePrevious` — confirmed dead in production, not a migration target

`TurnDaemonCommandDispatcher.kt:113-133` builds one shared `previousPointReader` at construction: when `inheritanceRepository` (type `opensamguk.infra.read.InheritanceRepository`, a live exact-key `game_kv` JPA read) is supplied, **every** handler (`placeBet`, `inheritReset`, the auction bid path via the same shared reader at `:308`) uses that live per-owner query, never the `state.meta["inheritancePrevious"]` snapshot. `DaemonLoopConfig.kt:202` declares `inheritanceRepository` as a **non-nullable, required** constructor parameter and wires it through at `:448`/`:462` — so in production this parameter is always present, and the meta-snapshot branch inside each handler's default parameter is unreachable code today. It exists only so handlers can be constructed standalone in tests without a repository. **Conclusion:** removing `inheritancePrevious` from boot meta (once `inheritancePoints` is bound per §A #5, the derivation becomes cheap and low-risk either way) requires no handler changes; at most, the now-always-unreachable default branches could be left as-is (harmless dead code exercised only by tests) or cleaned up as an optional follow-up — not a blocking parity risk.

## C. Tests

1. **Catalog ratchet test** (extend `HotColdWorldCatalogGuardTest` or add a sibling in `app/game-engine/src/test/kotlin/opensamguk/engine/boot/`): assert `HotColdCatalog.snapshotAccesses.none { it.bound == AccessBound.LEGACY_FULL_SCAN_PENDING_S5_T2 }`. Red today (5 entries use it); green only once every entry in §A is reclassified. This is a **regression ratchet** — if a future change reintroduces an unbounded boot scan and mislabels it, this fails immediately, mirroring how `DaemonWriteGuard` already works for the write path.
2. **SQL-text bound check**, extending the `PhaseHotQueryIsBoundedTest` (S5-T1) style to the new bounded reader methods: for each of §A's replacement queries, assert the source text contains an exact-key predicate (`= ?` / `= ANY(`), a `LIMIT 1`, or an aggregate function (`ORDER BY ... DESC LIMIT 1`, `MAX(`) — i.e., none of them is a bare `SELECT ... FROM <table>` with no bound. This catches a lazy re-introduction of an unbounded query at review time, before it reaches the query-count IT.
3. **Boot query/row-count IT** (new Testcontainers IT, `app/game-engine/src/test/kotlin/opensamguk/engine/boot/`, reusing the counting-`DataSource`-proxy technique from the S5-T1 design's `PhaseBoundaryQueryCountIT`): build two fixtures with identical hot cardinality (same generals/nations/cities) but `log_entry`/`statistic`/`game_kv` inheritance rows differing 10×; boot the daemon against each; assert (a) the boot-time SQL statement count is identical between fixtures (proving no query scales with row count) and (b) `TurnWorldState.meta` after boot no longer contains `statisticRows`/`nationHistory`/`generalHistory`/`globalLogs` keys at all (a direct, cheap proxy for "retained heap does not scale with history size" that does not require JFR tooling this repo does not have). Flag explicitly in the test's KDoc that this is the **build-only minimal substitute** for the GH AC's literal "3회 heap/JFR comparison" — a true retained-heap/GC delta measurement would need a JFR capture harness this repo does not currently have, and is called out as a non-goal below rather than fabricated with an unreliable `Runtime.totalMemory()` heuristic.
4. **Per-reader unit tests**: `StatisticSnapshotReaderTest` (peak-row / latest-row / empty-table edge cases), a history-archive-read test at the `JdbcFlushExecutor` layer (zero-history general, many-history general, ordering), `GlobalLogWindowReaderTest` (exact year/month/category boundaries, cross-month non-leak), and an id-bound test for the `loadRankValues`/`loadInheritancePoints` fix (asserts a general **not** in the loaded id set is excluded — this is the actual bug the current unscoped scan has today: it silently retains rows for generals from other/dead runs).
5. **Parity gate re-run**: unlike S5-T1 (design/catalog-only, no behavior change), this ticket changes real execution — every migrated call site must be re-verified against its existing golden/IT (general-death archive, nation-dissolution archive, emperor-coronation, monthly yearbook) via `tools/parity/gate.sh backend`, per repo discipline ("on a mismatch, fix the Kotlin impl, never the golden").

### Non-goals (explicitly out of scope for this ticket)

- **True JFR/GC retained-heap measurement.** This repo has no JFR capture harness. §C.3's query/row-count IT is the build-only minimal proxy; standing up real JFR tooling (or adopting a different team-approved metric per the GH AC's own "다른 승인된 수치가 있으면 그 값을 사용" allowance) is a separate, later investment, not blocking this ticket.
- **`ARCH-S1-T3` (`OPENSAM-125`/`#271`) capacity thresholds.** Unrelated admission-policy work; still open, not a dependency of this ticket.
- **`ARCH-S5-T3` (`OPENSAM-139`/`#285`) `committedWorldVersion`/`minVersion` primary-read barrier.** A read-consistency concern for API endpoints, not memory residency — orthogonal to this ticket.
- **Multi-world scoping of `log_entry`/`rank_data`/`game_kv`/`statistic`.** None of these four tables has a `world_id` column today (confirmed against `V1__baseline.sql`/`V7__p6_messaging_economy.sql`/`V13__statistic_table.sql`); this design only bounds the **quantity** read (one entity / one window / one id-list instead of everything), it does not add cross-world isolation. If the repo ever runs concurrent worlds against these specific tables, that is a separate, pre-existing gap, not introduced or fixed here.
- **`registerAuction()` phase-hot prefetch activation.** That is S5-T1's own deferred activation step, gated on `#271`; unrelated to this ticket's boot-scan removal.
- **Production deploy/cutover.** Per repo policy, no merge-to-main deploy without explicit human go-ahead; this ticket's own dependency line has no ticket-specific activation gate, but the general no-deploy-without-approval rule still applies.
- **Cleaning up the now-unreachable `inheritancePrevious` meta-snapshot default branches in `PlaceBetHandler`/`AuctionBidHandler`/`InheritResetHandler`/`InstantActionHandler`.** Confirmed dead in production (§B.2); leaving them as test-only fallbacks is harmless and not required by this ticket's AC.
