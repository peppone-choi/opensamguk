# PEP recovery verification implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Provide a fail-closed, scoped game-server backup and isolated restore rehearsal before the separately authorized PEP promotion/reset.

**Architecture:** Extend the existing operations tooling with an offline cold-volume bundle and isolated restore verifier. Production writer quiescence and lifecycle/promotion remain operator-controlled; this helper NEVER stops, starts, resets, removes or changes a production container/volume. Capture requires all five selected server containers already stopped; verification uses newly allocated, labeled resources with no published ports and no production network. The cold bundle preserves the entire PostgreSQL and Redis data directories, server environment, server compose definition, and exact current images. Restore means replaying this bundle, not lifecycle repair/reseed.

**Tech Stack:** Python 3 standard library, Docker CLI, PostgreSQL 16, Redis 7; unittest and real local Docker tests.

**Spec:** User-approved PEP-only recovery preparation and isolated restore rehearsal (2026-09-05); current `docs/admin/operations-and-recovery.md` and `docs/admin/server-lifecycle.md` define the existing fail-closed gate. Scope classification: bounded addition to the existing backup workflow, not a general disaster-recovery service.

## Global constraints

- Public target `pep`; internal `spep`; project `opensamguk-spep`. The helper accepts a canonical alphanumeric server ID, rejects `all`, reserved IDs, traversal and confirmation mismatch before any Docker mutation. Live execution selects only pep.
- Do not change other servers, shared account DB/Redis, registry, shared scenario directory, production volumes or image pins. Do not weaken existing reset/promotion workflows in this task.
- All project edits in the current bin/start-task worktree. No credentials, raw backups, raw env or private corpus in Git/public logs. Do not run git operations in reference repositories.
- New backup directories mode0700, files0600. Fail on existing output directory/symlink and ensure selected output is below the explicit backup root; no automatic retention deletion. Retain for at least30days AND until successful rollout/rollback acceptance; retention here is an operator minimum, not an automated SLA.
- For this PEP run, storage is the existing GCP encrypted-at-rest VM disk; access is VM root/authorized operator only. No new third-party storage, cloud snapshot of shared data, or key policy. This does NOT protect against whole-VM/disk loss; do not claim disaster recovery.
- Recovery point is the last committed DB state after app writers are stopped. In-memory unflushed work is not claimed recovered. Record capture and restore elapsed time; operational RTO target30minutes, not a proven guarantee until measured.
- Require exact named volumes (`s<ID>-game-pgdata`, `s<ID>-game-redisdata`), actual container compose project/service labels, expected mount destinations and stopped states. Reject unexpected extra mounts, PostgreSQL tablespace/WAL symlink arrangements and unsupported layouts rather than silently omitting data.
- Archive all five current image IDs once; record image refs and IDs. Helpers run by exact already-inspected database image ID, never mutable latest tags. Docker default local socket only for live use; no shell interpretation of user input.
- Bundles have versioned strict manifests and SHA256/size for every payload. Validate complete required file inventory and hashes BEFORE allocating/extracting restore resources. Reject archive traversal, links and unsafe entries before extraction. A manifest is integrity metadata, not an attacker-proof signature; filesystem access restrictions are part of the trust boundary.
- Restore only to fresh uniquely named/labeled scratch volumes. Never use production volume names as restore destinations. Cleanup may delete only resources created by this invocation after exact name/label checks. Failed cleanup must be reported, never hidden. Preserve the source bundle.
- Test-first on behavioral guards. Independent review before commit. Parent controls all live operations, commit/PR/merge. No subagents from implementer.

## Review-driven prerequisites

The independent task review found three required corrections: manual destructive rollback must abort on every failed precondition; a failed revalidation must invalidate an earlier success; and live shutdown/capture/resume must retain the production lock continuously. Task 1 will add same-instance, same-process/thread lock reentrancy without exposing a CLI bypass. Its CLI remains production-read-only. Live execution stays blocked until a separately reviewed operator harness provides the wider lock scope.

External scenario bind contents are not part of the storage bundle. Application rehearsal and any recovery acceptance require separately preserved or unchanged verified effective inputs; storage success does not claim a self-contained application backup.

### Task 2: Reviewed PEP-only cold-capture operator harness

This is a prerequisite to the already authorized live backup, not authority to reset, promote or reconcile registry metadata. A single same-process harness must hold `Recovery.locked()` before stopping any PEP container until the original containers have resumed and the maintenance barrier has been released. It may call the reentrant `capture` method, but never bypass the lock, recreate containers, change image pins, remove volumes, restore production data, mutate Gateway rows or run lifecycle repair.

Implementation details and the task brief will be finalized after the independent engine/control boundary audit. Required acceptance cases include refusal before mutation for wrong targets, unexpected source identities or preexisting maintenance; maintenance drain before intake stop; stable paused/recovery-ready state and empty nonterminal inbox before engine stop; private committed DB evidence before clean data shutdown; source bundle preservation; exact original IDs on ordered restart; and explicit failure reporting without a false success or unverified automatic recovery. Live execution and application restore rehearsal remain parent-controlled.

**Audit gate:** the current control service's maintenance enter actively cancels an existing operation, while maintenance GET `open` does not prove the service is idle. The source workflow flock does not supply an atomic no-active-operation proof for every direct control caller. Therefore do not implement or execute a harness that assumes `open` means safe admission. A non-cancelling atomic maintenance path or separately authorized operator coordination must be established first. This control-plane change and the stale Gateway transition reconciliation require the user's pending direction; Task 1 storage tooling can be independently integrated without claiming live verification.
