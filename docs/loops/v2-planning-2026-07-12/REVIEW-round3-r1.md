## CRITICAL

### C1 — `nation.gold` 미러 불변식이 구현 불가능 (`:91` §2.3)

`nation.gold`를 읽거나 쓰는 지점이 `logic/` + `app/game-engine/`에 **120곳, 20+ 파일** — `ProcessWarIncome`, `UpdateNationLevel`, `ConquerCity`, `CheHeonnap`(헌납), `ChePosang`(포상), `CheGamchuk`/`CheJeungchuk`, `Event*Yeongu` 병종연구 5종, AI `NationRewardFamily`·`GenFoundFamily` 등. 세 갈래가 전부 막혀 있다:

- (a) 120곳을 도시 원장 경유로 변경 → **v1 프로덕션 파일 편집**, §7.1 방어선 2 + ADR-LITE-018 직접 위반. R3 한 티켓 규모가 아니다
- (b) v2가 20개 파일 포크·복제 → R3 산출물과 자릿수가 다르고 이중 진실이 20배
- (c) flush에서 `nation.gold = Σ ledger` 재계산 → 그 턴 v1 커맨드의 `nation.gold` 델타(헌납·포상·연구비·정복 노획)를 **전부 소거**. 자원 소실

§2.3이 미러를 두는 이유로 든 "v1 precheck가 `nation.gold`를 읽는다"도 미러로 해결되지 않는다 — 총액 precheck는 통과하는데 차감은 특정 도시 원장에서 나가므로 **precheck가 구조적으로 거짓 통과**한다.

**요구**: §2.3 재작성. (i) v2에서 `nation.gold`를 읽는 v1 precheck·커맨드 전수 목록 + 각각의 처리(포크/차단/의미 재정의), (ii) 미러가 읽기전용 파생값인지 쓰기가능 이중원장인지, (iii) flush 검증 실패 시 동작. 없으면 R3 착수 불가.

### M0 — §2.2 "해법은 중복이다"의 전제가 코드상 거짓 (`:76-78`) ← 설계를 **줄이는** 수정

도시별 내역은 **이미 공개 API로 존재한다.** `logic/.../domestic/IncomeTick.kt`:
```kotlin
fun calcCityGoldIncome(city, officerCnt, isCapital, nationLevel, nationType, pipeline): Int  // :29
// :47 calcCityRiceIncome, :65 calcCityWallRiceIncome — 셋 다 top-level fun, 도시 1개당 Int
```
그리고 `getGoldIncome`의 국가 항은 `:117-123`에서 한 줄이다:
```kotlin
for (c in cityList) cityIncome += calcCityGoldIncome(c, officerCntByCity[c.id] ?: 0, capitalId == c.id, …)
```

즉 `V2CityIncome(city) = calcCityGoldIncome(city, …) * (taxRate/20)` — **v1 0줄 수정, 공식 재작성 0줄, 중복 0줄.** 골든 검증된 공식을 두 번째 파일에 옮겨 적는 것은 불필요할 뿐 아니라 이중 진실이다. 저자가 취약점 5로 적은 "v1을 잠깐만 리팩터링하고 싶은 압력"은 **존재하지 않는 압력**이었다 — 원인이 이 잘못된 전제다.

**요구**: §2.2를 "기존 per-city 함수를 그대로 호출하고 `taxRate/20`만 도시별 적용"으로 재작성. R2 산출물이 "`V2CityIncome` 순수 함수" → "귀속 어댑터 + 잔차 규칙"으로 줄고, Σ 불변식은 구성상 자명해진다.

### M1 — 공백지화 leaf가 같은 재난에 최대 3회 발화 (`:102, 118-129`)

설계안 스스로 "공백지화는 독립 스캔이 아니라 도적 사건 안의 후속 판정"이라 못 박고, 바로 아래 의사코드가 정확히 그 매턴 스캔이다. `city.state`는 매턴 초기화되지 않는다 — `RaiseDisaster.kt:24-27`의 `state=0` 리셋은 **`RaiseDisaster` 내부**에 있고 그 leaf 자체가 **1/4/7/10월에만 실행**된다(`:13`, `BOOMING_RATE` 키 `{1,4,7,10}`). 1월 stateCode가 4월 리셋 전까지 3개월 살아 있어 1·2·3월 각각 attrition이 걸린다. `LogicEntities.kt:77`의 "transient 1개월" 주석은 리셋 주기를 보장하지 않는다.

### M2 — 유일성 인덱스가 `role` 방향성과 모순되고, 그 인덱스를 담을 컬럼이 없다 (`:369, 373, 422`)

A→B `GRUDGE{OFFENDER,VICTIM}` 이후 B가 A를 해치면 유일성 키 `(world, GRUDGE, EMERGENT, {A,B})`가 **완전히 동일** → 새 결속 없이 `decay_at_turn`만 갱신되고 **방향 역전이 조용히 삼켜진다.** 상호 원한 표현 불가, `role`과 유일성 규칙이 서로를 부정한다. `MENTOR`(MASTER/DISCIPLE)도 같다. 둘째, `v2_general_bond`는 구성원 1명 = 1행이라 "구성원 집합"을 값으로 가진 컬럼이 **없다** — 제시된 인덱스는 이 스키마 위에 SQL로 표현 불가능하다.

**요구**: (i) 유일성 키에 방향을 넣거나 방향성 kind(MENTOR·GRUDGE·RESCUE)를 유일성 대상에서 빼고 재발생 시 새 `bond_id` 발급, (ii) 멤버셋 유일성을 강제할 실제 컬럼(정렬 멤버 해시)을 스키마에 추가하거나 강제를 애플리케이션 레이어로 명시적으로 내린다.

### M3 — 우선순위 규칙이 적대 보정을 사문화 (`:395` + `:339-340`)

`SWORN > MENTOR > RESCUE > COMRADE > GRUDGE > RIVAL`에서 `COMRADE` 생성 조건은 "같은 `Operation` 참가 후 작전 종료"다. 작전이 v2 기본 전쟁 단위이므로 같은 국가 장수 대부분이 개막 몇 턴 안에 서로 `COMRADE`가 된다 → **한 번이라도 같이 싸웠으면 원한·라이벌은 영구히 발현되지 않는다.** 남는 −2 사례는 타국 소속뿐인데 조건이 "같은 도시"로 좁혀져 있어 사실상 없다. **−2는 코드에 있고 게임에 없다.**

**요구**: 적대 kind를 최상위로 올리거나, 우호/적대를 **별도 축으로 각각 1회 적용 후 합산·클램프**(후자가 규칙 3·4와 정합).

### M4 — `±6` 상한은 실효 상한이 아니다. v1 교차증강이 뚫는다 (`:397`)

`logic/.../stats/GetStatValue.kt:54-64`:
```kotlin
if (withStatAdjust) {
    "strength" -> v += phpRound(crossBase("intelligence", …))
    "intelligence" -> v += phpRound(crossBase("strength", …))
}
v = clamp(v, 0.0, maxLevel); if (withIActionObj) v = pipeline.onCalcStat(...)  // 관계 모듈 발화
```
`crossBase`가 `getStatValue(other, …, withIActionObj = withIActionObj)`를 **재귀 호출**하므로(`:89-91`) 교차증강 경로에서도 관계 모듈이 발화한다. 지력 +6 → 무력은 자기 몫 +6에 더해 `phpRound(6/4) = +2` 추가 = **실효 +8.** "상한의 존재는 계약"이라 선언했는데 계약이 아니다.

**요구**: 교차증강 상호작용을 §4.7에 명시하고 (a) 실효 상한 재계산·표기 **[현실적]**, 또는 (b) `withStatAdjust=false` 재귀에서 관계 모듈 identity — 단 플래그 전달 경로가 없어 현 인터페이스로는 불가.

**덧 — `±6 < lbonus +14` 비교의 부정확성.** 범주 오류는 아니다(저자가 "패러티 방어가 아니라 밸런스 근거"로 스스로 한정). 그러나 `OfficerLevelModule.kt:39-47`상 `lbonus`는 (i) **통솔 한 스탯에만**, (ii) `+14`는 `officerLevel==12` = 국가당 **군주 1명** × `nationLevel==7`(황제국)일 때뿐, (iii) 일반 관직자(`>=5`)는 `nationLevel` 그대로다. 관계 보정은 **3스탯 전부·모든 장수·lbonus와 가산 중첩**. "이미 존재하는 가장 큰 보정보다 작게"는 성립하지 않는다 — 밸런스 근거로도 재작성 필요.

### M5 — RTK 원본 인물관계 필드 존재를 미검증 단정 (`:304`)

근거로 든 `docs/superpowers/specs/2026-07-18-scenario-system.md:90-92`는 **"원천에 없는 것(→ 시드 기본/후속)"** 제목 아래 있고 본문은 "인물관계(被親愛/被嫌悪)도 **정제층 미포함** → v2"다. 인용 근거는 *정제층에 없다*만 확립하며 *원본에는 있다*를 확립하지 않는다 — 제목은 오히려 반대를 말한다. 이 설계안은 최소 10곳에 UNKNOWN을 붙일 만큼 규율이 있는데 **하필 자기 데이터 공급원 하나만 단정형**이다. §4.4 출처 2와 §9.3 "사전 관계 전면 데이터" 계획 전체가 이 단정 위에 서 있다.

**요구**: `:304`를 "RTK 원본에 인물관계 필드가 있는지는 **UNKNOWN**, 확인 전까지 출처 2는 후보"로 정정하거나 1차 근거(RTK14 데이터 구조 실측) 제시.

### M6 — §9.2 삽입 위치가 R5·R6 의존성과 모순 (`:699-704, 750`)

§9.5는 "삽입 위치는 3단계(V2-0B) 직후"라 단정하는데, R5(병사보충)·R6(수송) 산출물에 "intake 배선 + result 규약"이 있고 §2.5가 그것을 OPENSAM-13/135 `pollCommandResult`로 명시한다. 그 lifecycle은 **4단계 OPENSAM-45·46·47(V2-1)**이다. R5·R6은 3단계 직후에 놓일 수 없다.

**요구**: 티켓별 삽입 단계를 개별 표기(R1~R4 = 0B 직후, R5·R6 = V2-1 이후, R7 = V2-3/V2-5, R8 = R7 이후). 단일 단정 철회.

### M7 — R7이 한 티켓이 아니고, R8에 표시 경로가 빠져 +8이 방어되지 않는다 (`:705-710`)
